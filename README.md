# Training Application

Учебное приложение, упакованное в Docker-образ. То же самое приложение, что в Task 2 работало под управлением systemd.

---

## Application

Простейший HTTP-сервер на Bash. На каждое обращение возвращает одну и ту же текстовую строку, не разбирая ни путь, ни метод запроса.

```bash
#!/bin/bash
while true; do
    if [ -f /tmp/crash ]; then
        echo "$(date '+%H:%M:%S') trigger file found, shutting down"
        exit 1
    fi
    echo "$(date '+%H:%M:%S') waiting for connection on port 9000"
    echo -e "HTTP/1.1 200 OK\nContent-Type: text/plain\n\n$APP_MESSAGE" | nc -l -p 9000
    echo "$(date '+%H:%M:%S') client served"
    echo "$(date '+%H:%M:%S') Client Served" >> /data/requests.log
done
```

**Как это работает:**

| Элемент | Назначение |
|---|---|
| `while true` | `nc` обслуживает одно соединение и завершается — без цикла сервер умер бы после первого запроса |
| `nc -l -p 9000` | слушает TCP-порт 9000, **блокирует** выполнение до прихода клиента |
| `echo ... \| nc` | вывод уходит в сокет, то есть клиенту |
| `echo ...` без пайпа | вывод идёт в stdout, откуда его забирает Docker |
| `$APP_MESSAGE` | текст ответа берётся из переменной окружения, а не зашит в код |
| `>> /data/requests.log` | дописывание в файл, для проверки постоянного хранения |
| проверка `/tmp/crash` | управляемое падение — механизм из Task 2 |

Разделение вывода принципиально: строка с пайпом идёт клиенту, строка без пайпа — в журнал. Позиция относительно `nc` тоже значима: строка выше блокирующего вызова означает «начал ждать», ниже — «обслужил и закрыл».

Пакет netcat — **`netcat-openbsd`**. Реализации netcat различаются флагами; с другой версией вызов `nc -l -p 9000` не отработает.

**Ограничение:** сервер обслуживает одно соединение за раз. В `ss` это видно как `Send-Q 1` — длина очереди ожидающих подключений (у nginx для сравнения 4096).

## Docker Image

```dockerfile
FROM ubuntu:24.04
RUN mkdir -p /data
RUN apt update && apt install -y netcat-openbsd
COPY app/app.sh /app/app.sh
RUN chmod +x /app/app.sh
EXPOSE 9000
CMD ["/app/app.sh"]
```

**Сборка:**

```bash
cd ~/training-app
docker build -t training-app:1.2 .
```

Точка в конце — контекст сборки, каталог, откуда Docker берёт файлы для `COPY`. Копировать файлы **выше** контекста нельзя, поэтому скрипт заранее положен в `app/`.

### Разбор инструкций

| Инструкция | Что делает | Почему так |
|---|---|---|
| `FROM ubuntu:24.04` | базовый образ | Скрипт начинается с `#!/bin/bash`. В Alpine стоит BusyBox `sh`, `/bin/bash` отсутствует — контейнер упал бы при старте. Тег указан явно: `latest` со временем меняется, и образ, собранный через полгода, окажется другим |
| `RUN mkdir -p /data` | каталог для данных | `>>` создаёт файл, но не каталог. Без этого — `No such file or directory` |
| `RUN apt update && apt install -y ...` | зависимости | `&&` объединяет в один слой: раздельно `apt update` закешируется, и установка пойдёт по устаревшему списку. `-y` обязателен — при сборке некому отвечать на запрос подтверждения. `sudo` не нужен, сборка идёт от root |
| `COPY app/app.sh /app/app.sh` | скрипт в образ | Источник относительно контекста, назначение — абсолютный путь |
| `RUN chmod +x` | право на исполнение | `COPY` сохраняет права исходного файла. Без бита `x` — `permission denied`. В Dockerfile надёжнее, чем на хосте: образ не зависит от машины сборки |
| `EXPOSE 9000` | объявление порта | **Ничего не открывает.** Только метаданные образа. Реальный проброс делает `-p` при запуске |
| `CMD ["/app/app.sh"]` | команда старта | JSON-форма (exec form). Процесс запускается напрямую, без оболочки |

### Почему CMD в форме JSON

Shell-форма `CMD /app/app.sh` разворачивается в `/bin/sh -c "/app/app.sh"` — PID 1 достаётся оболочке, скрипт становится её потомком. При `docker stop` сигнал уходит оболочке, та его не передаёт, и Docker убивает контейнер через `SIGKILL` по таймауту.

JSON-форма запускает скрипт напрямую. В `docker ps` это видно по колонке COMMAND: `"/app/app.sh"` без обёртки.

### Размер и слои

```
training-app:1.2   208MB
nginx:latest       241MB
```

Собственный код занимает пару килобайт — почти весь объём это базовая Ubuntu (~78 MB) и apt-кеш. Кеш можно было убрать, дописав `&& rm -rf /var/lib/apt/lists/*`.

Три собранные версии (1.0, 1.1, 1.2) занимали не 624 MB, а заметно меньше: слои `FROM` и `RUN` общие, различался только последний слой со скриптом.

**Порядок инструкций влияет на кеш.** Docker переиспользует слои до первого изменения; всё после пересобирается. Правило — располагать от редко меняющихся к часто меняющимся. В текущем файле `RUN mkdir` стоит перед `apt install`, из-за чего его сдвиг заставил пересобирать apt-слой.

## Container

**Запуск:**

```bash
docker run -d --init \
  --name data-test-4 \
  -p 9000:9000 \
  -e APP_MESSAGE="Hello from training-app" \
  -v app-data:/data \
  training-app:1.2
```

| Флаг | Назначение |
|---|---|
| `-d` | detach — фоновый режим, терминал возвращается сразу |
| `--init` | подставляет `docker-init` как PID 1 (см. ниже) |
| `--name` | имя контейнера; без него Docker генерирует случайное вроде `magical_goldstine` |
| `-p 9000:9000` | проброс порта, хост:контейнер |
| `-e` | переменная окружения |
| `-v app-data:/data` | том, монтируется в `/data` |

### Зачем `--init`

Без этого флага `docker stop` занимал ровно **10.238 секунды**, с ним — **0.210 секунды**.

Причина: ядро Linux не доставляет сигналы процессу с PID 1, если тот не установил обработчик явно. Bash-скрипт обработчика не ставит, поэтому `SIGTERM` от `docker stop` игнорируется. Docker ждёт таймаут и добивает через `SIGKILL`.

`--init` подставляет первым процессом `docker-init`, скрипт становится обычным потомком и получает сигналы нормально:

```
575834  /sbin/docker-init -- /app/app.sh    ← PID 1
   └─ 575878  /bin/bash /app/app.sh
        └─ 575881  nc -l -p 9000
```

Вторая функция `docker-init` — сбор процессов-сирот, чтобы внутри контейнера не накапливались зомби.

**Альтернатива:** `trap` в самом скрипте — тогда сигнал обрабатывается приложением, и флаг не нужен. Для реального сервиса предпочтительнее: даёт возможность корректно завершиться, закрыть файлы, дописать данные.

### Изоляция

**PID namespace.** Процессы имеют разные номера снаружи и внутри:

| Процесс | PID на хосте | PID в контейнере |
|---|---|---|
| главный | 575834 | 1 |
| скрипт | 575878 | ~7 |
| nc | 575881 | ~8 |

Внутри контейнера главный процесс видит себя первым в системе и не может обнаружить ни один процесс хоста.

**Network namespace.** У контейнера собственный сетевой стек: свой интерфейс, свой IP, свой набор портов. Поэтому несколько контейнеров могут слушать один и тот же порт внутри себя без конфликта — столкнуться они способны только на хосте, при пробросе.

**Пользователь.** Процессы в контейнере работают от **root**, если не указано иное. В systemd-версии этой задачи приложение было переведено на отдельного пользователя `training-app`; в контейнерной версии это пока не сделано. Правильное решение — `RUN useradd` и инструкция `USER` в Dockerfile.

## Ports

**Конфигурация:** `-p 9000:9000`

```
9000 (хост) : 9000 (контейнер)
```

Левая часть — порт хоста, правая — порт внутри контейнера. Пара не обязана быть симметричной: второй контейнер в Part 5 запускался как `-p 9001:9000`, потому что 9000 на хосте был уже занят. Порт внутри при этом остался прежним — он зашит в скрипт.

### Как это устроено

```
curl localhost:9000
   ↓
docker-proxy         ← слушает порт на ХОСТЕ
   ↓
docker0 (172.17.0.1) ← мост, шлюз для контейнеров
   ↓
veth-пара            ← виртуальный «патч-корд» между namespace
   ↓
eth0 (172.17.0.2)    ← интерфейс внутри контейнера
   ↓
nc слушает :9000
```

Проверка на хосте показывает, что порт держит **не приложение**:

```
tcp LISTEN 0 4096 0.0.0.0:9000 users:(("docker-proxy",pid=574250,fd=8))
```

`docker-proxy` — обычный процесс, принимающий соединения на порту хоста и переправляющий их в сеть контейнера. Это и есть реализация `-p`.

Интерфейсы на хосте:

```
docker0: inet 172.17.0.1/16              ← мост
veth01f7d41@if2: master docker0          ← один конец пары
                 link-netnsid 0
```

Запись `@if2` указывает на второй конец — интерфейс с индексом 2 внутри контейнера. У хостового конца нет IPv4-адреса: он работает на канальном уровне и просто передаёт кадры в мост.

### Практические следствия

**Без `-p` контейнер работает, но снаружи недоступен.** Одна из причин для вопроса «почему контейнер запущен, а приложение не отвечает».

**Неверный порт в правой части — та же картина.** При `-p 8080:8080` вместо `-p 8080:80` контейнер nginx покажет статус `Up`, а `curl` вернёт ошибку: Docker честно перенаправит трафик на порт 8080 контейнера, где никто не слушает.

**Адрес клиента в логах.** Приложение видит `172.17.0.1` — шлюз `docker0`, а не реальный IP пользователя. Настоящий адрес теряется при NAT; в реальных схемах его передают заголовком `X-Forwarded-For`.

**Сеть контейнеров доступна с хоста напрямую** — `curl http://172.17.0.2:9000` работает без всякого проброса. Но с другой машины этот адрес недостижим, для внешнего доступа и нужен `-p`.

## Environment Variables

| Переменная | Назначение | Значение по умолчанию |
|---|---|---|
| `APP_MESSAGE` | текст, возвращаемый клиенту | нет — при отсутствии тело ответа будет пустым |

**Передача:**

```bash
docker run -e APP_MESSAGE="Hello from container 1" training-app:1.2
```

**Проверка внутри контейнера:**

```bash
docker exec container-1 env | grep APP_MESSAGE
```

### Демонстрация

Два контейнера из **одного образа** с разным поведением:

```bash
docker run -d --init --name container-1 -p 9000:9000 \
  -e APP_MESSAGE="Hello from container 1" training-app:1.1

docker run -d --init --name container-2 -p 9001:9000 \
  -e APP_MESSAGE="Hello from container 2" training-app:1.1
```

```
$ curl http://localhost:9000   →  Hello from container 1
$ curl http://localhost:9001   →  Hello from container 2

$ docker exec container-1 env | grep APP_MESSAGE
APP_MESSAGE=Hello from container 1
$ docker exec container-2 env | grep APP_MESSAGE
APP_MESSAGE=Hello from container 2
```

### Зачем это нужно

**Один артефакт на все среды.** С зашитыми значениями пришлось бы держать отдельный образ на каждую конфигурацию: dev, staging, production. Тогда в продакшен уезжает не тот образ, который тестировали. С переменными один собранный и проверенный образ проходит весь путь, меняется только окружение.

**Секреты не попадают в образ.** Пароль, вшитый в слой, извлекается через `docker history` — даже если строку впоследствии удалили. Слои неизменяемы, и удаление файла в следующем слое не убирает его из предыдущего.

**Возможное улучшение:** значение по умолчанию. Инструкцией `ENV APP_MESSAGE="..."` в Dockerfile либо конструкцией `${APP_MESSAGE:-значение}` в скрипте — тогда контейнер, запущенный без `-e`, вернёт осмысленный ответ вместо пустого тела.

## Persistent Storage

| Том | Точка монтирования | Содержимое |
|---|---|---|
| `app-data` | `/data` | `requests.log` — запись по одной строке на обслуженный запрос |

**Подключение:**

```bash
docker run -v app-data:/data training-app:1.2
```

Слева имя тома, справа путь внутри контейнера. Если тома не существует, Docker создаст его автоматически.

### Эксперимент

**Без тома:**

```
$ docker exec data-test cat /data/requests.log
09:21:32 Client Served
09:21:34 Client Served
09:21:36 Client Served

$ docker stop data-test && docker rm data-test
$ docker run -d --name data-test-2 ... training-app:1.2
$ docker exec data-test-2 cat /data/requests.log
cat: /data/requests.log: No such file or directory
```

**С томом:** после удаления и пересоздания контейнера с тем же `-v app-data:/data` записи оказались на месте.

### Почему данные пропали в первый раз

Контейнер — это неизменяемый образ плюс тонкий **записываемый слой** поверх. Всё, что процесс пишет во время работы, ложится в этот слой, и слой живёт ровно столько же, сколько контейнер: `docker rm` удаляет их вместе.

Новый контейнер получил **чистый** слой поверх того же образа. Каталог `/data` в нём есть — он часть образа, создан инструкцией `RUN mkdir`. Файла нет: его создал предыдущий контейнер в своём слое, который уничтожен.

### Почему пережили с томом

Том — отдельная сущность, живущая вне контейнера, в `/var/lib/docker/volumes/`. При запуске Docker монтирует его в указанную точку, подменяя этот каталог в файловой системе контейнера. Приложение пишет как обычно, но данные оказываются на хосте.

Проверяется напрямую, без контейнера:

```bash
docker volume inspect app-data
sudo cat /var/lib/docker/volumes/app-data/_data/requests.log
```

Удаление контейнера тома не касается — он остаётся до явного `docker volume rm`.

**Общий принцип:** контейнеры одноразовые, их удаляют и пересоздают при каждом обновлении образа. Всё, что должно это пережить — базы данных, загруженные файлы, логи — выносится в тома.

**Замечание про `--init`:** без корректной обработки сигналов приложение убивается через `SIGKILL` и не успевает дописать данные. Для приложения, пишущего в файл, это реальный риск потери последних записей.

## Useful Commands

### Запуск

```bash
docker run -d --init --name data-test-4 -p 9000:9000 \
  -e APP_MESSAGE="Hello" -v app-data:/data training-app:1.2
```

Создаёт **новый** контейнер. Для запуска существующего:

```bash
docker start data-test-4
```

### Остановка

```bash
docker stop data-test-4      # SIGTERM, затем SIGKILL через 10 с
docker kill data-test-4      # сразу SIGKILL
```

### Перезапуск

```bash
docker restart data-test-4
```

### Логи

```bash
docker logs data-test-4              # весь вывод
docker logs -f data-test-4           # следить в реальном времени
docker logs --tail 20 data-test-4    # последние 20 строк
docker logs --since 10m data-test-4  # за последние 10 минут
```

Docker перехватывает stdout и stderr главного процесса — тот же принцип, по которому journald собирал вывод в systemd-версии. Файл лежит в `/var/lib/docker/containers/<ID>/<ID>-json.log` и растёт без ограничений, пока не настроена ротация.

### Инспекция

```bash
docker ps                          # работающие контейнеры
docker ps -a                       # включая остановленные
docker inspect data-test-4         # полная конфигурация (JSON)
docker inspect data-test-4 | jq '.[0].NetworkSettings'
docker top data-test-4             # процессы внутри
docker stats data-test-4           # потребление ресурсов в реальном времени
docker port data-test-4            # проброшенные порты
```

Структура вывода `inspect` различается между версиями Docker: шаблон `{{.NetworkSettings.IPAddress}}` в версии 29 не работает, адрес перенесён в `.NetworkSettings.Networks.bridge.IPAddress`. Универсальный вариант:

```bash
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' data-test-4
```

### Вход в контейнер

```bash
docker exec -it data-test-4 bash     # интерактивная оболочка
docker exec data-test-4 env          # разовая команда
docker exec data-test-4 cat /data/requests.log
```

`-i` держит stdin открытым, `-t` выделяет псевдотерминал. Выход — `exit`.

`docker exec` работает только с **запущенным** контейнером. Для остановленного посмотреть содержимое можно через `docker cp` или запустив новый контейнер из того же образа.

### Сборка и образы

```bash
docker build -t training-app:1.2 .
docker images
docker rmi training-app:1.0 training-app:1.1
docker history training-app:1.2      # слои образа
```

### Тома

```bash
docker volume ls
docker volume inspect app-data
docker volume rm app-data
```

### Уборка

```bash
docker system df          # что сколько занимает
docker rm <контейнер>     # удалить контейнер
docker rmi <образ:тег>    # удалить образ
docker builder prune      # очистить кеш сборки
```

**Порядок важен:** образ нельзя удалить, пока на нём есть контейнер, даже остановленный.

**Флаг `-f` у `docker rm`** нужен только для работающих контейнеров — он посылает `SIGKILL` и удаляет. Без него Docker откажется удалять активный контейнер и предупредит, что защищает от опечатки в имени.

**`docker system prune` без разбора** удаляет всё неиспользуемое разом, включая то, что удалять не планировалось. Перед уборкой правильнее посмотреть состояние четырьмя командами (`ps`, `ps -a`, `images`, `volume ls`) и удалять адресно.

**Кеш сборки живёт отдельно от образов.** После удаления версий 1.0 и 1.1 `docker system df` показывал 300 MB кеша, из которых 91 MB подлежали освобождению. На машинах, где часто собирают образы, кеш разрастается до десятков гигабайт — типичная причина заполнения диска.

## Cleanup

Состояние до уборки:

| Объект | Статус |
|---|---|
| `data-test-4` (training-app:1.2) | Up — нужен |
| `docker_task` (nginx) | Up — нужен |
| `magical_goldstine` (hello-world) | Exited 2 hours ago — удалить |
| `training-app:1.0`, `1.1` | без контейнеров — удалить |
| `hello-world:latest` | занят остановленным контейнером |
| `app-data` | том с данными — оставить |

Колонка `In Use` в `docker images` помечает образы, на которых есть контейнеры. `hello-world` был помечен как используемый, хотя его контейнер давно остановлен — отсюда порядок уборки: сначала контейнеры, затем образы.

Итог:

```
TYPE            TOTAL  ACTIVE  SIZE     RECLAIMABLE
Images          2      2       449.4MB  0B (0%)
Containers      2      2       98.3kB   0B (0%)
Local Volumes   1      1       69B      0B (0%)
Build Cache     13     0       300MB    91.33MB
```

`RECLAIMABLE 0B` по образам, контейнерам и томам подтверждает, что лишнего не осталось. Единственный кандидат на освобождение — кеш сборки.

## Сравнение с systemd

То же приложение под управлением двух разных систем:

| | systemd (Task 2) | Docker (Task 3) |
|---|---|---|
| Запуск | `systemctl start` | `docker run` |
| Описание конфигурации | юнит-файл | Dockerfile |
| Логи | `journalctl -u` | `docker logs` |
| Куда пишет приложение | stdout | stdout |
| Кто перехватывает | journald | Docker daemon |
| Где хранится | `/var/log/journal/` | `/var/lib/docker/containers/<ID>/` |
| Изоляция | пользователь + права файлов | namespaces + cgroups |
| Зависимости | ставятся на хост | зашиты в образ |
| Автозапуск | `systemctl enable` | `--restart` |
| Перезапуск при падении | `Restart=always` | `--restart unless-stopped` |
| Конфигурация | `Environment=` в юните | `-e` при запуске |
| Данные | обычные файлы на хосте | том |

Механизм логирования принципиально одинаков: приложение пишет в stdout, менеджер перехватывает. Требование «write a message to stdout» из Task 2 окупилось дважды.

Главное различие — в зависимостях. Системная версия требовала установленного `netcat-openbsd` на хосте; контейнер несёт его с собой. Версия nginx в контейнере (1.31.4) отличается от системной, и они сосуществуют без конфликта.

## AI Assistance

### Почему `docker stop` занимает ровно 10 секунд

**Вопрос:** остановка контейнера стабильно длилась 10.238 с, хотя приложение простое.

**Объяснение:** ядро Linux не доставляет сигналы процессу с PID 1, если тот не установил обработчик явно — защита от случайного убийства `init`. Bash-скрипт обработчика не ставит, `SIGTERM` игнорируется, Docker ждёт таймаут и применяет `SIGKILL`.

**Что понял:** PID 1 в контейнере — особая роль, а не просто первый процесс. Это влияет и на обработку сигналов, и на сбор процессов-сирот.

**Как проверил:** пересоздал контейнер с `--init` и замерил:

```
без --init:  real 0m10.238s
с --init:    real 0m0.210s
```

`docker top` подтвердил новую иерархию: `docker-init` первым, скрипт под ним.

### Структура вывода `docker inspect`

**Вопрос:** шаблон `{{.NetworkSettings.IPAddress}}` вернул `map has no entry for key "IPAddress"`.

**Объяснение:** в Docker 29 сетевые данные перенесены в `.NetworkSettings.Networks.<имя сети>.IPAddress`.

**Что понял:** формат вывода меняется между версиями, и команду из документации нельзя применять не глядя.

**Как проверил:** посмотрел фактическую структуру через `docker inspect | grep -A30 NetworkSettings`, нашёл верный путь. Универсальный вариант с `range` работает независимо от имени сети.

### Различие `EXPOSE` и `-p`

**Вопрос:** нужен ли `EXPOSE`, если порт всё равно пробрасывается флагом.

**Объяснение:** `EXPOSE` не открывает порт, а записывает его в метаданные образа как документацию. Реальный проброс делает только `-p`.

**Как проверил:** запустил nginx с ошибочным `-p 8080:8080` вместо `-p 8080:80`. Контейнер показал статус `Up`, `curl` не получил ответа — при том что `EXPOSE 80` в образе присутствует. Подтверждает, что инструкция ничего не открывает.

### Выбор базового образа

**Вопрос:** можно ли взять Alpine вместо Ubuntu ради размера.

**Объяснение:** в Alpine используется BusyBox `sh`; `/bin/bash` отсутствует. Шебанг `#!/bin/bash` указывает конкретный путь, и контейнер упал бы при старте.

**Что понял:** дело не в синтаксисе скрипта — он POSIX-совместим и работал бы в `sh`, — а именно в пути из шебанга. С Alpine пришлось бы либо ставить bash отдельным пакетом, либо менять шебанг.

**Компромисс:** Ubuntu даёт 208 MB против ~10 MB у Alpine. Для учебной задачи приемлемо, для продакшена стоило бы оптимизировать.

## Final Questions

**1. Разница между образом и контейнером.** Образ — неизменяемый шаблон: файловая система плюс метаданные о том, что запускать. Контейнер — запущенный экземпляр образа с собственным записываемым слоем. Из одного образа создаётся сколько угодно контейнеров; проверено в Part 5, где два контейнера из `training-app:1.1` отвечали по-разному.

Аналогия: скрипт `app.sh` на диске — образ, процесс с конкретным PID — контейнер.

**2. Что происходит при удалении контейнера.** Удаляется его записываемый слой со всеми изменениями файловой системы. Образ и тома не затрагиваются.

**3. Что происходит с файлами внутри контейнера.** Живут ровно столько, сколько контейнер. Проверено: `requests.log` исчез после `docker rm`, хотя новый контейнер создавался из того же образа.

**4. Зачем нужны тома.** Контейнеры одноразовые — их пересоздают при каждом обновлении образа. Тома живут отдельно, в `/var/lib/docker/volumes/`, и переживают удаление контейнера. Всё, что должно сохраняться — базы, загрузки, логи — выносится в них.

**5. Что означает `8080:80`.** Порт 8080 хоста перенаправляется на порт 80 внутри контейнера. Реализуется процессом `docker-proxy`, который слушает на хосте и переправляет трафик через мост `docker0` и veth-пару в сетевой namespace контейнера.

**6. Почему контейнер может работать, а приложение быть недоступно.** Статус `Up` означает лишь, что главный процесс жив. Причины недоступности: неверный порт в правой части `-p`; отсутствие `-p` вообще; приложение слушает `127.0.0.1` внутри контейнера вместо `0.0.0.0`; порт занят на хосте; приложение упало, но PID 1 продолжает работать.

**7. Как посмотреть вывод приложения.** `docker logs <контейнер>`. Docker перехватывает stdout и stderr главного процесса — поэтому приложение должно писать именно туда, а не в собственный файл.

**8. Как узнать, почему контейнер завершился.** `docker ps -a` покажет код выхода в колонке STATUS — например `Exited (0)` или `Exited (1)`. `docker logs` покажет последние строки перед смертью. `docker inspect` содержит `State.ExitCode` и `State.OOMKilled` — последнее указывает на нехватку памяти.

**9. Почему конфигурацию и секреты не зашивают в образ.** Образ становится привязан к одной среде, и приходится собирать отдельный на каждую — тогда в продакшен уезжает не тот артефакт, который тестировали. Секреты в слоях извлекаются через `docker history` даже после удаления файла: слои неизменяемы, и удаление в следующем слое не убирает данные из предыдущего.

**10. Преимущество одного образа с разными переменными.** Собран и протестирован один раз, проходит весь путь от dev до production без пересборки. Различия задаются извне, при запуске. Проверяемость: артефакт в проде побайтно тот же, что тестировали.
