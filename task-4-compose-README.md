# Task 4 — Docker Compose & Multi-Container Application

Среда из трёх сервисов под управлением Docker Compose: reverse proxy, приложение, база данных.

---

## Architecture

```
                    Host
                     │
                     │ :8080  ← единственный проброшенный порт
                     ▼
        ┌────────────────────────┐
        │  nginx:1.27            │
        │  слушает :80           │
        │  reverse proxy         │
        └───────────┬────────────┘
                    │  сеть task-4_default
                    │  proxy_pass → http://app:9000
                    ▼
        ┌────────────────────────┐
        │  app (свой образ)      │
        │  слушает :9000         │
        │  Python http.server    │
        └───────────┬────────────┘
                    │  сеть task-4_default
                    │  psycopg2 → postgres:5432
                    ▼
        ┌────────────────────────┐
        │  postgres:16           │
        │  слушает :5432         │
        └───────────┬────────────┘
                    │
                    ▼
            volume task-4_pgdata
            (данные переживают пересоздание контейнера)
```

**Порты 9000 и 5432 на хост не пробрасываются.** Снаружи доступен только nginx. Приложение и база достижимы исключительно внутри сети Compose.

### Почему приложению нужно несколько контейнеров

**Независимое обновление.** Код приложения меняется часто, PostgreSQL — почти никогда. В одном контейнере любая правка требовала бы пересборки образа вместе с базой и её перезапуска.

**Независимое масштабирование.** При росте нагрузки запускают несколько копий приложения на одну базу. Склеенные вместе, они дали бы несколько независимых баз с разными данными.

**Разный жизненный цикл.** Контейнер приложения одноразовый: удалил, пересоздал из нового образа. У базы — том, который должен пережить всё. Требования к устойчивости противоположные.

**Готовые образы.** PostgreSQL уже собран и поддерживается разработчиками. Устанавливать его внутрь своего образа — повторять чужую работу хуже.

**Изоляция сбоев.** Проверено в Part 6: падение базы не роняет приложение, падение приложения не роняет прокси.

### Разделение ответственности

| Сервис | Отвечает за |
|---|---|
| **nginx** | единственная точка входа снаружи, проксирование запросов приложению, приём медленных и некорректных соединений |
| **app** | бизнес-логика: маршрутизация по путям, обращение к базе, формирование ответа |
| **postgres** | хранение данных, переживающих перезапуск и пересоздание приложения |

## Services

### nginx

```yaml
  nginx:
    image: nginx:1.27
    ports:
      - "8080:80"
    volumes:
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      - app
```

**Версия зафиксирована явно.** Тег `latest` со временем указывает на разные образы: собранная сегодня среда через полгода получила бы другой nginx. Воспроизводимость теряется.

**Единственный сервис с секцией `ports`.** Пара `8080:80` — слева порт хоста, справа порт внутри контейнера.

**Конфиг подключён bind mount'ом**, а не скопирован в образ. Правка файла на хосте применяется перезапуском контейнера, пересборка не нужна. Суффикс `:ro` делает монтирование read-only — контейнер не может изменить файл.

Конфигурация:

```nginx
server {
    listen 80;
    resolver 127.0.0.11 valid=10s;
    set $upstream http://app:9000;

    location / {
        proxy_pass $upstream;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

**`resolver 127.0.0.11`** — адрес встроенного DNS-сервера Docker.

**`proxy_pass` через переменную**, а не литеральное имя — принципиальное решение, разобрано в разделе Networking.

**`proxy_set_header`** передают исходные данные клиента дальше. Без них приложение видело бы только адрес прокси.

### app

```yaml
  app:
    build: ./app
    environment:
      DB_HOST: postgres
      DB_NAME: ${DB_NAME}
      DB_USER: ${DB_USER}
      DB_PASSWORD: ${DB_PASSWORD}
    depends_on:
      - postgres
```

**`build` вместо `image`** — образ собирается из локального Dockerfile, а не тянется из реестра.

**Секции `ports` нет** — наружу сервис не смотрит, обращается к нему только nginx через внутреннюю сеть.

Dockerfile:

```dockerfile
FROM python:3.12-slim
RUN pip install --no-cache-dir psycopg2-binary
COPY app.py /app/app.py
EXPOSE 9000
CMD ["python3", "/app/app.py"]
```

| Инструкция | Обоснование |
|---|---|
| `python:3.12-slim` | urезанный образ ~150 МБ против ~1 ГБ у полного. Инструменты сборки приложению не нужны |
| `psycopg2-binary` | готовый бинарник; обычный `psycopg2` требует компиляции и системных библиотек PostgreSQL |
| `--no-cache-dir` | pip не сохраняет скачанные пакеты в слой образа |
| `EXPOSE 9000` | только документация в метаданных, порт не открывает |
| `CMD` в JSON-форме | процесс запускается напрямую через `execve()`, без обёртки `/bin/sh -c` |

Приложение — HTTP-сервер на `http.server` из стандартной библиотеки. Фреймворк не использовался: для двух эндпоинтов избыточен, а без него видно механику маршрутизации.

**Эндпоинты:**

| Путь | Поведение |
|---|---|
| `GET /` | вставляет строку в таблицу `visits`, возвращает счётчик обращений |
| `GET /health` | проверяет соединение с базой, возвращает раздельный статус приложения и БД |

```
$ curl http://localhost:8080
Hello from app
Visits: 3

$ curl http://localhost:8080/health
Application: OK
Database: OK
```

**Соединение с базой создаётся на каждый запрос**, внутри обработчика, а не один раз при старте. Следствия разобраны в разделе Failure Testing.

### postgres

```yaml
  postgres:
    image: postgres:16
    environment:
      POSTGRES_DB: ${DB_NAME}
      POSTGRES_USER: ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - pgdata:/var/lib/postgresql/data
```

**Официальный образ**, версия зафиксирована.

**Имена переменных `POSTGRES_*` заданы самим образом** — при первом запуске его entrypoint читает их и создаёт базу с пользователем. Менять нельзя.

**Портов нет.** База недоступна с хоста, только из сети Compose.

**`/var/lib/postgresql/data`** — путь, где PostgreSQL хранит данные, определён образом.

Таблица создаётся приложением при старте:

```sql
CREATE TABLE IF NOT EXISTS visits (
    id SERIAL PRIMARY KEY,
    ts TIMESTAMP DEFAULT NOW()
)
```

`IF NOT EXISTS` позволяет вызывать это при каждом запуске приложения безопасно.

Фактическая структура:

```
 Column |            Type             | Nullable |              Default
--------+-----------------------------+----------+------------------------------------
 id     | integer                     | not null | nextval('visits_id_seq'::regclass)
 ts     | timestamp without time zone |          | now()
Indexes:
    "visits_pkey" PRIMARY KEY, btree (id)
```

`SERIAL` — не настоящий тип, а сокращение: PostgreSQL создаёт `integer`, отдельную последовательность `visits_id_seq` и привязывает её как значение по умолчанию.

## Networking

### Сеть создаётся автоматически

Секции `networks` в `docker-compose.yml` нет — Compose создаёт сеть проекта сам и подключает к ней все сервисы:

```json
"Name": "task-4_default",
"Driver": "bridge",
"IPAM": {
    "Config": [{ "Subnet": "172.18.0.0/16", "Gateway": "172.18.0.1" }]
},
"Labels": {
    "com.docker.compose.project": "task-4",
    "com.docker.compose.network": "default"
}
```

Имя составлено из имени проекта (взято из имени каталога) и `default`.

**Это пользовательская сеть, и разница принципиальна.** Дефолтная сеть `bridge` (`172.17.0.0/16`, где работали контейнеры в предыдущем задании) **не имеет встроенного DNS** — там контейнеры видят друг друга только по IP. В пользовательских сетях Docker поднимает DNS-сервер на `127.0.0.11`, резолвящий имена сервисов.

Именно поэтому связка по именам работает без дополнительной настройки.

### Адреса контейнеров

```
task-4-postgres-1   172.18.0.2
task-4-app-1        172.18.0.3
task-4-nginx-1      172.18.0.4
```

Адреса выданы последовательно, в порядке запуска — он определён цепочкой `depends_on`.

### Как сервисы находят друг друга

**Приложение → база:** переменная `DB_HOST=postgres`, значение попадает в `psycopg2.connect(host=...)`.

**Nginx → приложение:** `proxy_pass http://app:9000` в конфигурации.

В обоих случаях используется **имя сервиса** из `docker-compose.yml`. Docker DNS превращает его в актуальный IP.

### Почему имя сервиса, а не хардкоженный IP

**Адрес не гарантирован.** Выдаётся динамически при создании контейнера. После `docker compose down && up` порядок запуска может измениться, добавление сервиса сдвинет распределение — числа поедут.

**Ошибка была бы молчаливой.** Пропиши в `proxy_pass` адрес `172.18.0.3` — после смены адреса конфигурация останется синтаксически валидной, nginx запустится нормально, а запросы будут уходить в никуда. Диагностировать пришлось бы по 502 без единой ошибки при старте.

Сравнить можно с тем, что произошло при неверном **имени**: nginx упал сразу, с `[emerg]`, указав файл и строку. Ошибка видна немедленно.

**Имя — контракт.** `postgres` в `app.py` и `app` в конфигурации nginx совпадают с ключами сервисов в `docker-compose.yml`. Переименование сервиса ломает связь заметно. У IP такой связи нет вовсе.

**Масштабирование.** При запуске нескольких копий приложения DNS вернёт все адреса, и запросы распределятся. С одним прописанным IP работала бы одна копия.

**Проверено экспериментом.** После полного пересоздания среды (`down` + `up`, сеть удалена и создана заново) приложение продолжило работать:

```
$ docker compose down && docker compose up -d
$ curl http://localhost:8080/health
Application: OK
Database: OK
```

### Отладка резолвинга: два наблюдения

При первом запуске nginx падал:

```
[emerg] 1#1: host not found in upstream "app" in /etc/nginx/conf.d/default.conf:5
```

**Первая гипотеза — поисковый домен.** Проверка через временный контейнер в той же сети:

```
$ docker run --rm --network task-4_default busybox nslookup app
Server:  127.0.0.11
** server can't find app.local: NXDOMAIN
```

Резолвер спрашивал **`app.local`**, а не `app`. Причина видна в `/etc/resolv.conf` контейнеров:

```
nameserver 127.0.0.11
search local
options edns0 trust-ad ndots:0
# Based on host file: '/etc/resolv.conf'
```

Строка `search local` унаследована от хоста. Механизм: резолвер дописывает суффикс к коротким именам, получается `app.local`, которого Docker DNS не знает.

Замечание: при `ndots:0` имя без точек должно проверяться как абсолютное в первую очередь, поэтому такое поведение специфично для резолвера busybox — реализации различаются.

**Гипотеза опровергнута для nginx.** Добавление точки (`app.`) не помогло — ошибка повторилась с именем `"app."`. Проверка тем же образом, что использует nginx, показала работающий DNS:

```
$ docker run --rm --network task-4_default nginx:1.27 getent hosts app
172.18.0.3      app
```

**Вторая гипотеза — момент резолвинга.** Nginx разрешает имена из `proxy_pass` **один раз при разборе конфигурации**, при старте. Если имя недоступно в этот момент — процесс завершается с `[emerg]`.

`depends_on` не спасает: он ждёт **запуска** контейнера, а не готовности DNS-записи или самого сервиса.

**Решение — перенести резолвинг на время обработки запроса:**

```nginx
resolver 127.0.0.11 valid=10s;
set $upstream http://app:9000;
proxy_pass $upstream;
```

Когда в `proxy_pass` стоит переменная, nginx резолвит имя при каждом запросе через указанный `resolver`, а не при старте. Стартовая проверка отпадает.

**Побочная польза подтвердилась в Part 6:** при остановленном `app` nginx не упал, а вернул 502 и продолжил работать. С литеральным именем он бы не пережил перезапуск при недоступном бэкенде.

### Конфликты портов

За время работы возникло три конфликта за порты на хосте:

| Порт | Кто занимал |
|---|---|
| 9000 | systemd-сервис из предыдущего задания |
| 8080 | контейнер nginx из предыдущего задания |
| 8080 | повторно, при `docker compose up` |

```
Error response from daemon: failed to set up container networking:
Bind for :::8080 failed: port is already allocated
```

Причина общая: **контейнеры изолированы внутри себя, но делят пространство портов хоста при публикации**. Внутри контейнеров конфликта нет — несколько сервисов могут слушать один порт в своих namespace. Столкновение возникает только на стороне хоста.

## Configuration

### Переменные окружения

| Переменная | Сервис | Назначение | Источник |
|---|---|---|---|
| `POSTGRES_DB` | postgres | имя создаваемой базы | `${DB_NAME}` из `.env` |
| `POSTGRES_USER` | postgres | имя пользователя БД | `${DB_USER}` из `.env` |
| `POSTGRES_PASSWORD` | postgres | пароль | `${DB_PASSWORD}` из `.env` |
| `DB_HOST` | app | имя хоста базы | задано прямо: `postgres` |
| `DB_NAME` | app | имя базы | `${DB_NAME}` из `.env` |
| `DB_USER` | app | пользователь | `${DB_USER}` из `.env` |
| `DB_PASSWORD` | app | пароль | `${DB_PASSWORD}` из `.env` |

**Одни и те же значения** из `.env` уходят и в postgres (для создания базы), и в app (для подключения). Рассинхрона быть не может.

**`DB_HOST` не вынесен в `.env`** — это имя сервиса из самого `docker-compose.yml`, не секрет и не переменная среды развёртывания.

### Как это работает

**В приложении:**

```python
db_host = os.environ.get("DB_HOST", "postgres")
db_name = os.environ.get("DB_NAME", "appdb")
db_user = os.environ.get("DB_USER", "appuser")
db_password = os.environ.get("DB_PASSWORD", "")
```

Второй аргумент — значение по умолчанию. У пароля дефолт **пустой намеренно**: реальный пароль в коде оказался бы в git.

**Цепочка подстановки:**

```
.env  →  ${DB_NAME} в compose  →  DB_NAME=... в окружении контейнера  →  os.environ.get("DB_NAME")
```

### Секреты

**`.env`** содержит реальные значения и **не коммитится** — добавлен в `.gitignore` до его создания:

```
.env
*.log
__pycache__/
```

Проверка:

```
$ git status --untracked-files=all
	.gitignore
	task-4/.env.example
	task-4/app/Dockerfile
	task-4/app/app.py
	task-4/docker-compose.yml
	task-4/nginx/default.conf
```

`.env` в списке отсутствует, `.env.example` присутствует.

**`.env.example`** коммитится и показывает структуру без раскрытия значений:

```
DB_NAME=appdb
DB_USER=appuser
DB_PASSWORD=changeme
```

**Замечание:** `docker compose config` **разворачивает подстановки** и печатает пароли в открытом виде. Такой вывод нельзя вставлять в тикеты, переписку или запросы к внешним сервисам.

## Storage

| Том | Точка монтирования | Содержимое |
|---|---|---|
| `task-4_pgdata` | `/var/lib/postgresql/data` | файлы базы PostgreSQL |

Объявлен на верхнем уровне `docker-compose.yml`:

```yaml
volumes:
  pgdata:
```

Compose добавляет префикс проекта, фактическое имя — `task-4_pgdata`.

**Физическое расположение** — `/var/lib/docker/volumes/task-4_pgdata/_data/`, доступно с хоста без всякого контейнера:

```bash
docker volume inspect task-4_pgdata
sudo ls /var/lib/docker/volumes/task-4_pgdata/_data/
```

### Проверка сохранности

```
$ docker compose exec postgres psql -U appuser -d appdb -c "SELECT COUNT(*) FROM visits"
 count
-------
     3

$ docker compose stop postgres
$ docker compose rm -f postgres
$ docker compose up -d postgres

$ docker compose exec postgres psql -U appuser -d appdb -c "SELECT COUNT(*) FROM visits"
 count
-------
     3
```

**Контейнер удалён и создан заново — данные на месте.**

### Почему данные исчезли бы без тома

Контейнер — это неизменяемый образ плюс тонкий **записываемый слой** поверх. Всё, что процесс пишет во время работы, ложится в этот слой, и слой существует ровно столько же, сколько контейнер.

`docker rm` удаляет контейнер вместе со слоем. Новый контейнер получает **чистый** слой поверх того же образа: каталог `/var/lib/postgresql/data` в нём есть (он часть образа), но пуст. PostgreSQL счёл бы его новой установкой и инициализировал базу с нуля.

### Почему выжили с томом

Том — отдельная сущность, живущая вне контейнера. При запуске Docker монтирует его в указанную точку, **подменяя** этот каталог в файловой системе контейнера. PostgreSQL пишет по обычному пути, но данные оказываются в томе на хосте.

Удаление контейнера тома не касается. Он остаётся до явного `docker volume rm` или `docker compose down -v`.

**Общий принцип:** контейнеры одноразовые, их пересоздают при каждом обновлении образа. Всё, что должно это пережить — базы, загруженные файлы, накопленные данные — выносится в тома.

## Failure Testing

### Test 1 — остановлено приложение

```
$ docker compose stop app
$ curl -i http://localhost:8080
HTTP/1.1 502 Bad Gateway
Server: nginx/1.27.5
```

Ответ пришёл **от nginx**, не от приложения — видно по заголовку `Server` и HTML-странице из образа. Прокси работает, порт слушается, соединение устанавливается.

Причина в логе:

```
[error] 21#21: *17 app could not be resolved (2: Server failure),
        client: 172.18.0.1, request: "GET / HTTP/1.1"
```

**Сбой резолвинга, а не отказ соединения.** При остановке контейнера Docker убирает его запись из встроенного DNS — имя `app` перестаёт разрешаться.

**Nginx не упал**, отдал 502 и продолжил работать. Это следствие резолвинга через переменную: ошибка обрабатывается на уровне запроса, а не рушит процесс.

Различение симптомов:

| Симптом | Где проблема |
|---|---|
| `Connection refused` | некому слушать порт на хосте — упал nginx или порт не проброшен |
| `502 Bad Gateway` | nginx работает, бэкенд недоступен |
| `504 Gateway Timeout` | бэкенд отвечает, но слишком долго |
| `Connection timed out` | пакеты блокируются файрволом |

### Test 2 — остановлена база

```
$ docker compose stop postgres

$ curl http://localhost:8080/health
Application: OK
Database: FAIL (could not translate host name "postgres" to address: Temporary failure in name resolution)

$ curl http://localhost:8080
Hello from app
DB error: could not translate host name "postgres" to address: Temporary failure in name resolution
```

**Приложение не упало** — вернуло HTTP 200 с описанием проблемы. Работает `try/except`: исключение перехвачено, клиент получил ответ вместо оборванного соединения.

**`/health` разделяет статусы:** `Application: OK` и `Database: FAIL` — разные вещи, и мониторинг должен их различать.

**Снова DNS**, не отказ соединения. Механизм тот же, что в первом тесте: Docker DNS регистрирует только работающие контейнеры.

Полезное различение при диагностике:

| Сообщение | Что означает |
|---|---|
| `could not translate host name` | контейнер не запущен, DNS-записи нет |
| `Connection refused` | контейнер работает, но сервис внутри не слушает порт — упал или ещё инициализируется |

**Вывод текста исключения (`as e`) окупился** — без него был бы голый `FAIL` без указания причины.

### Test 3 — база возвращена

```
$ docker compose start postgres
$ curl http://localhost:8080/health
Application: OK
Database: OK
```

**Приложение восстановилось автоматически, без перезапуска.**

Причина в том, как написан код: `psycopg2.connect()` вызывается **внутри обработчика запроса**, то есть заново на каждое обращение. Неудачная попытка перехватывается `try/except` и не оставляет следов в состоянии приложения — следующий запрос выполняет подключение с нуля.

Иначе было бы при соединении, установленном один раз при старте: после падения базы объект соединения стал бы мёртвым, и приложение продолжало бы его использовать после возврата PostgreSQL. Помог бы только перезапуск контейнера.

**Обратная сторона решения.** Установка TCP-соединения и аутентификация на каждый запрос обходятся дорого: под нагрузкой это заметно скажется на задержке и создаст лишние подключения к базе. В production используют **пул соединений** — набор заранее открытых, переиспользуемых, с автоматическим восстановлением упавших. Для учебной задачи простой вариант оправдан и, как показал тест, устойчивее к сбоям.

### Test 4 — перезапуск всей среды

```
$ docker compose restart
$ docker compose ps
$ curl http://localhost:8080/health
Application: OK
Database: OK
```

Все сервисы поднялись, данные в томе сохранились.

### Общий вывод

Сбои **изолированы**: падение базы не роняет приложение, падение приложения не роняет прокси. Каждый уровень отвечает внятной ошибкой вместо тишины или зависания.

## AI Usage

### Почему nginx не резолвит имя сервиса при старте

**Вопрос:** nginx падает с `[emerg] host not found in upstream "app"`, при этом контейнер `app` работает.

**Первое предположение:** поисковый домен. Проверка через временный контейнер показала запрос к `app.local` вместо `app`, и в `/etc/resolv.conf` действительно обнаружилось `search local`, унаследованное от хоста.

**Как проверил:** добавил точку в конец имени (`app.`) — **гипотеза не подтвердилась**, ошибка повторилась с новым именем. Дополнительная проверка тем же образом, что использует nginx:

```
$ docker run --rm --network task-4_default nginx:1.27 getent hosts app
172.18.0.3      app
```

DNS работает.

**Что понял в итоге:** причина не в DNS, а в **моменте** резолвинга. Nginx разрешает имена из `proxy_pass` один раз, при разборе конфигурации на старте. `depends_on` этого не покрывает — он ждёт запуска контейнера, а не готовности DNS-записи.

**Проверка решения:** переписал конфигурацию с `resolver 127.0.0.11` и переменной в `proxy_pass`. Nginx поднялся. Побочный эффект подтвердился в Part 6: при остановленном `app` он не падает, а отдаёт 502.

Отдельный вывод: опровергнутая гипотеза — тоже результат. Точка в имени была логичным шагом, и её неудача сузила круг поиска.

### Почему docker compose down занимает 10 секунд на app

**Вопрос:** остановка контейнера приложения стабильно длится ~10 секунд.

**Объяснение:** ядро Linux не доставляет сигналы процессу с PID 1, если тот не установил обработчик явно. Python-скрипт обработчика не ставит, `SIGTERM` игнорируется, Docker ждёт таймаут и применяет `SIGKILL`.

**Что понял:** PID 1 в контейнере — особая роль, а не просто первый процесс.

**Как проверил:** тот же симптом наблюдался в предыдущем задании с bash-скриптом, и там подтвердился замером: 10.238 с без `--init` против 0.210 с с ним. Решение для Compose — `init: true` в описании сервиса либо обработчик сигнала в самом приложении.

**Статус:** в текущей конфигурации не применено, отмечено как возможное улучшение.

### Различение ошибок DNS и отказа соединения

**Вопрос:** при остановленной базе приложение возвращает `could not translate host name`, а не `Connection refused` — почему?

**Объяснение:** Docker DNS регистрирует только работающие контейнеры. Остановленный контейнер теряет запись, и обращение к нему падает на этапе разрешения имени, не доходя до попытки соединения.

**Что понял:** два текста ошибки указывают на разные стадии сбоя и позволяют быстро сузить диагностику — контейнер не запущен вообще либо запущен, но сервис внутри не готов.

**Как проверил:** наблюдал оба варианта. `could not translate host name` — при `docker compose stop postgres`. `Connection refused` возникал бы, если бы контейнер работал, но PostgreSQL внутри ещё инициализировался.

## Final Questions

**1. Какую проблему решает Docker Compose?**

Управление несколькими связанными контейнерами. Без него потребовалось бы вручную создавать сеть и том, затем запускать три `docker run` с длинными наборами флагов, в правильном порядке, каждый раз заново. Compose описывает всё одним YAML-файлом; среда поднимается одной командой, сеть и DNS настраиваются автоматически.

**2. Как контейнеры общаются между собой?**

Через сеть, созданную Compose для проекта. Каждый контейнер получает адрес в подсети (`172.18.0.0/16`) и подключается к мосту. Обращение идёт **по имени сервиса**, которое встроенный DNS-сервер Docker на `127.0.0.11` резолвит в актуальный IP.

**3. Почему приложение не использует localhost для подключения к PostgreSQL?**

У каждого контейнера собственный сетевой namespace: свой интерфейс, свой набор портов, свой loopback. `localhost` внутри контейнера приложения указывает на **сам этот контейнер**, где PostgreSQL нет. База живёт в другом контейнере, со своим независимым loopback. Это как два отдельных сервера — обращаться нужно по имени или адресу.

**4. Что такое сеть Docker?**

Виртуальная сеть, объединяющая контейнеры. Реализована мостом на хосте плюс парами `veth`, соединяющими сетевые namespace контейнеров с этим мостом. Пользовательские сети дополнительно получают встроенный DNS для разрешения имён сервисов — в дефолтной сети `bridge` его нет.

**5. Почему данные PostgreSQL должны быть в томе?**

Записываемый слой контейнера удаляется вместе с контейнером. Без тома пересоздание контейнера базы — при обновлении образа, изменении конфигурации, перезапуске среды — уничтожило бы все данные. Том живёт отдельно и переживает эти операции.

**6. Почему только nginx доступен с хоста?**

Единственная точка входа сокращает поверхность атаки: порты приложения и базы недостижимы снаружи. Nginx принимает на себя медленные и некорректные соединения. При масштабировании он распределяет запросы между копиями приложения, оставаясь одним адресом для клиента. База, доступная снаружи, — прямой риск.

**7. Что происходит при удалении контейнера?**

Удаляется его записываемый слой со всеми изменениями файловой системы. Образ, тома и сеть не затрагиваются.

**8. Что происходит при удалении контейнера PostgreSQL?**

При наличии тома — ничего страшного: данные остаются в томе, новый контейнер их подхватит. Проверено экспериментально: 3 записи до удаления, 3 после пересоздания. Без тома данные были бы потеряны безвозвратно.

**9. Как определить, почему сервис Compose не запускается?**

```bash
docker compose ps -a          # статус, включая упавшие
docker compose logs <сервис>  # причина
docker compose up <сервис>    # запуск в переднем плане, ошибка сразу видна
docker compose config         # проверка конфигурации
```

Флаг `-a` обязателен: упавший контейнер в обычном `ps` отсутствует, и это легко принять за то, что он не создавался. Запуск в переднем плане удобен тем, что ошибка выводится немедленно.

**10. В чём разница между внутренним портом контейнера и опубликованным портом хоста?**

Внутренний порт — тот, на котором приложение слушает в своём сетевом namespace. Он изолирован: несколько контейнеров могут занимать один и тот же номер без конфликта.

Опубликованный порт — точка на хосте, которую Docker связывает с внутренним через `-p` или секцию `ports`. Здесь пространство общее, и конфликт возможен — что подтвердилось трижды за время работы.

`EXPOSE` в Dockerfile не публикует порт, а только документирует его в метаданных образа.
