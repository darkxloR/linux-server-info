## Application

Простейший HTTP-сервер на Bash. На каждое обращение возвращает одну и ту же текстовую строку, не разбирая ни путь, ни метод запроса.

**Расположение:** `/opt/training-app/app.sh`

```bash
#!/bin/bash
while true; do
        if [ -f /tmp/crash ]; then
            echo "$(date '+%H:%M:%S') trigger file found, shutting down"
            exit 1
        fi
        echo "$(date '+%H:%M:%S') waiting for connection on port 9000"
        echo -e "HTTP/1.1 200 OK\nContent-Type: text/plain\n\nHello from training-app!" | nc -l -p 9000;
        echo "$(date '+%H:%M:%S') client served"
done
```

| Пункт | Значение |
|---|---|
| Application | HTTP-сервер, отдающий статичный текст |
| Language | Bash |
| How to start it | `systemctl start training-app` (вручную — `/opt/training-app/app.sh`) |
| How to stop it | `systemctl stop training-app`. При ручном запуске — `Ctrl+C`, а для фонового процесса нужно найти PID через `ss -tulpn` или `ps -ef` и послать сигнал командой `kill` |
| Port | 9000/tcp |

### Разбор скрипта

**`while true`** — `nc` обслуживает **одно** соединение и завершается. Без цикла сервер умер бы после первого запроса.

**`nc -l -p 9000`** — слушает порт и **блокирует** выполнение до прихода клиента. Это ключевое свойство: именно оно не даёт циклу крутиться вхолостую.

**Разделение вывода принципиально:**

| Строка | Куда идёт |
|---|---|
| `echo ... \| nc` | в сокет, то есть клиенту |
| `echo ...` без пайпа | в stdout, откуда его забирает journald |

**Позиция относительно `nc` тоже значима.** Строка выше блокирующего вызова означает «начал ждать», ниже — «обслужил и закрыл». Пара таких записей в журнале даёт готовый access-лог.

**Шебанг `#!/bin/bash`** обязателен именно для systemd. Ядро читает первые два байта файла и подставляет указанный интерпретатор. При запуске из оболочки bash подстрахует и без шебанга, а systemd делает `execve()` напрямую — без шебанга получил бы `203/EXEC`. Классическая причина ситуации «работает руками, но не работает как сервис».

### Проблема с netcat

Вызов `nc -l -p 9000` из задания не заработал сразу:

```
/opt/training-app/app.sh: line 6: nc: command not found
07:28:22 client served
07:28:22 waiting for connection on port 9000
/opt/training-app/app.sh: line 6: nc: command not found
07:28:22 client served
```

**Два вывода из этого лога:**

1. netcat не установлен в системе;
2. **все записи в одну секунду** — `nc` был единственной блокирующей командой, и без него цикл крутился на максимальной скорости, сжигая процессор.

Симптом стоит запомнить: множество одинаковых записей с одинаковой отметкой времени означает цикл без блокировки.

Установлен **`netcat-openbsd`** — конкретная реализация имеет значение, разные версии netcat понимают разные флаги.

## Linux User

```bash
sudo useradd -r -M -s /usr/sbin/nologin training-app
```

| Флаг | Что даёт | Обоснование |
|---|---|---|
| `-r` | системная учётка, UID ниже 1000 | по границе 1000 система отличает служебные учётки от человеческих; для системной не заводится политика устаревания пароля |
| `-M` | не создавать домашний каталог | сервису он не нужен; лишний каталог — лишнее место, доступное на запись при компрометации |
| `-s /usr/sbin/nologin` | оболочка, блокирующая вход | учётная запись нужна для запуска процесса, не для работы человека |

Ни один из трёх флагов в задании не назван — все выведены из требования «only the permissions required to run the application».

**Результат в `/etc/passwd`:**

```
training-app:x:996:989::/home/training-app:/usr/sbin/nologin
```

| Поле | Значение |
|---|---|
| имя | training-app |
| пароль | `x` — хеш в `/etc/shadow`, куда обычным пользователям доступа нет |
| UID | 996 — системный диапазон, `-r` сработал |
| GID | 989 — одноимённая группа создана автоматически |
| GECOS | пусто |
| домашний каталог | `/home/training-app` — **записан, но не создан** |
| оболочка | `/usr/sbin/nologin` |

Флаг `-M` отменяет создание каталога, но не запись о нём: `ls -ld /home/training-app` возвращает «No such file or directory».

### Почему nologin не мешает сервису

Проверено экспериментом:

```bash
$ sudo -u training-app whoami
training-app
```

Сработало, хотя вход заблокирован.

**Причина:** `nologin` блокирует **интерактивный вход** — SSH, консоль, `su`. Все они пытаются запустить пользователю оболочку и натыкаются на заглушку.

`sudo -u` и systemd работают иначе: они вызывают программу напрямую через `execve()`, минуя оболочку. Поле shell в `/etc/passwd` в этом пути вообще не участвует.

Итог: **процесс запускается, человек войти не может** — ровно то, что нужно сервисной учётной записи.

**Выбор между `nologin` и `/bin/false`.** Оба блокируют вход. `nologin` печатает `This account is currently not available` и завершается, `/bin/false` молча возвращает код 1. Для сервисной учётки берут `nologin` ради читаемости: администратору, выясняющему, почему вход не проходит, внятное сообщение экономит время.

## File Permissions

```
drwxr-xr-x  root root  /opt/training-app
-rwxr-xr-x  root root  /opt/training-app/app.sh
```

**Владелец — root, менять не потребовалось.** Это осознанное решение, а не бездействие.

`training-app` не владелец и не входит в группу root, значит попадает в категорию «остальные», где стоит `r-x`: чтение и исполнение, без записи.

**Проверено фактами, а не рассуждением:**

```bash
sudo -u training-app cat /opt/training-app/app.sh          # читает
sudo -u training-app /opt/training-app/app.sh              # запускается
sudo -u training-app touch /opt/training-app/test.txt      # Permission denied
```

**Почему не отдали каталог пользователю.** Приложению нужно только читать и исполнять свой скрипт; писать в каталог оно не должно. При `chown training-app` скомпрометированный сервис смог бы переписать `app.sh` и закрепиться в системе — его код запускался бы при каждом старте. Текущая схема этого не позволяет.

### Права на каталогах читаются иначе, чем на файлах

| Бит | На каталоге |
|---|---|
| `r` | можно посмотреть список файлов (`ls`) |
| `x` | можно войти внутрь и обратиться к файлу по имени |
| `w` | можно создавать и удалять файлы внутри |

Тонкость: удаление файла определяется правом `w` на **каталоге**, а не на самом файле. Можно удалить файл, в который тебе запрещено писать.

### Ответы на вопросы Part 2

**Кто владеет файлами приложения?** root:root — и каталог, и скрипт.

**Под каким пользователем идёт процесс?**

```
$ ps -o user,pid,ppid,cmd -p 29748
USER         PID    PPID CMD
trainin+   29748       1 /bin/bash /opt/training-app/app.sh
```

`trainin+` — имя обрезано до 8 символов. `PPID 1` означает, что родитель — systemd.

**Может ли другой обычный пользователь изменить приложение?** Нет. У `sard` и `Tigran` права категории «остальные» — `r-x`, записи нет.

**Может ли пользователь приложения лезть туда, куда не должен?** Ограничен обычными правами Unix: не пишет в свой каталог, не входит в систему, не состоит в дополнительных группах. Но читать общедоступные файлы вроде `/etc/passwd` может — стандартные права этого не запрещают. Более жёсткая изоляция делается директивами systemd (`ProtectSystem`, `PrivateTmp`), в этой работе не применялась.

## systemd Configuration

**Файл:** `/etc/systemd/system/training-app.service`

```ini
[Unit]
Description=Simple HTTP server listening on port 9000
After=network.target

[Service]
Type=simple
ExecStart=/opt/training-app/app.sh
User=training-app
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

**Почему `/etc/systemd/system/`:** каталоги `/lib/systemd/system/` и `/usr/lib/systemd/system/` предназначены для юнитов из пакетов, их перезаписывает `apt`. `/etc/systemd/system/` — для локальных, созданных администратором, и у него приоритет.

### [Unit] — метаданные и связи

**`Description`** — показывается в `systemctl status` и в списках юнитов. Требование задания — осмысленный текст: из него должно быть понятно, что за сервис и на каком порту, не открывая файл.

**`After=network.target`** — задаёт **порядок**: если сеть тоже поднимается, стартовать после неё.

Три директивы зависимостей легко перепутать:

| Директива | Смысл |
|---|---|
| `After=X` | только порядок. Если X не запускается — сервис всё равно стартует |
| `Wants=X` | постарайся запустить X. Если не вышло — сервис работает дальше |
| `Requires=X` | без X не работаю. Упадёт X — остановят и сервис |

Выбран `After`: `network.target` поднимается сам при загрузке, отдельно запускать его не нужно. `Requires` был бы избыточно жёстким — при кратковременной проблеме с сетью ронять сервис смысла нет, он продолжит работать, просто без клиентов.

Отдельно стоит знать разницу `network.target` и `network-online.target`: первая означает, что сетевая подсистема запущена, вторая — что адрес реально получен. Для приложения, слушающего на всех интерфейсах, достаточно первой.

### [Service] — параметры процесса

**`Type=simple`** — systemd считает сервис запущенным сразу после старта процесса. Подходит, потому что скрипт работает в переднем плане, не форкается и сам не завершается.

Альтернативы: `forking` — для демонов, уходящих в фон; `oneshot` — для задач, которые отрабатывают и выходят.

`simple` — значение по умолчанию, но указано явно: читающему юнит сразу видно намерение, а не приходится помнить умолчания.

**`ExecStart`** — только абсолютный путь. Относительный systemd не примет: у него нет «текущего каталога» в том смысле, в каком он есть у оболочки.

**`User=training-app`** — от кого запускать.

**`Restart=always`** — перезапуск после **любого** завершения, включая выход с кодом 0.

Выбор между `always` и `on-failure` осмысленный. `on-failure` поднимает только при ненулевом коде, завершении сигналом или таймауте. Но приложение — бесконечный цикл, который при нормальной работе не завершается **никогда**. Значит любое его завершение аномально, включая чистый выход. Поэтому `always`.

**`RestartSec=5`** — пауза перед перезапуском. Значение по умолчанию 100 мс; при мгновенно падающем приложении это привело бы к сотням перезапусков в секунду.

### [Install] — автозагрузка

Секция читается **только** командами `systemctl enable` и `disable`. При обычном `start` не используется. Без неё `enable` вернёт ошибку — прописывать ссылку некуда.

**`WantedBy=multi-user.target`** — стандартное состояние сервера: система загружена, сеть есть, графики нет.

Ошибочный выбор `graphical.target` привёл бы к неприятному сценарию: `enable` отработает без ошибок, ссылка создастся, а при загрузке система дойдёт до `multi-user.target` и остановится — до графической цели она не доходит. Сервис не запустится, и **никакой ошибки в журнале не будет**.

Проверить целевое состояние системы: `systemctl get-default`.

## Service Management

```bash
sudo systemctl daemon-reload      # обязательно после правки юнита
sudo systemctl start training-app
sudo systemctl enable training-app
systemctl status training-app
```

**`daemon-reload` обязателен.** systemd кеширует юниты и новый или изменённый файл сам не заметит. Забыть про него — классическая ошибка: правишь файл, перезапускаешь сервис, а поведение прежнее.

**`start` и `enable` — разные вещи.** Первый запускает сейчас, второй создаёт символическую ссылку в `multi-user.target.wants/` для следующей загрузки. Требование задания «Start automatically after boot» выполняется вторым.

| Вопрос | Команда | Ответ |
|---|---|---|
| Работает ли сервис? | `systemctl status` | `active (running)` |
| Какой PID? | `systemctl status` | главный 570064; плюс дочерний `nc` с **меняющимся** PID |
| Какой пользователь? | `ps -o user,pid,ppid,cmd -p <PID>` | `training-app`, PPID = 1 |
| Какой порт? | `sudo ss -tulpn \| grep 9000` | 9000, слушает `nc`, не скрипт |
| Где логи? | `journalctl -u training-app` | системный журнал |
| Сколько работает? | `systemctl status` | строка `Active: since ...` |
| Что при рестарте? | `restart` + сравнение | новый PID, счётчики обнуляются |

### Два процесса, две роли

```
$ sudo ss -tulpn | grep 9000
tcp LISTEN 0 1 0.0.0.0:9000 users:(("nc",pid=569990,fd=3))
```

**Порт держит `nc`, а не скрипт.**

| Процесс | Роль |
|---|---|
| `app.sh` | главный процесс сервиса (`Main PID`), крутит цикл, пишет в журнал |
| `nc` | дочерний, занимает порт, обслуживает клиента и умирает |

`Main PID` — то, что systemd запустил через `ExecStart`. Следит он именно за ним: умрёт скрипт — сработает `Restart=always`. За потомками systemd не следит, они попадают только в CGroup.

Практическое следствие: **PID у `nc` меняется после каждого клиента** — 569957 → 569990 → 570069. Каждая итерация цикла порождает новый процесс.

Поэтому на вопрос «What PID does the application have?» правильный ответ не одно число, а объяснение: главный процесс имеет стабильный PID, а порт слушает короткоживущий дочерний с постоянно меняющимся номером.

**`Send-Q 1`** в выводе `ss` — backlog, длина очереди ожидающих соединений. У nginx для сравнения 4096. Единица отражает устройство `nc`: он обслуживает одно соединение за раз.

**`fd=3`** — номер файлового дескриптора. Дескрипторы 0, 1, 2 всегда заняты под stdin, stdout, stderr, поэтому первый свободный именно 3.

### CGroup

```
CGroup: /system.slice/training-app.service
        ├─570064 /bin/bash /opt/training-app/app.sh
        └─570069 nc -l -p 9000
```

Контрольная группа — механизм ядра, которым systemd отслеживает и ограничивает процессы сервиса. Показывает **все** процессы деревом, включая порождённые.

Практическая польза: при `systemctl stop` systemd убивает группу целиком, а не только главный процесс. Осиротевшего `nc` не останется — ровно та проблема, с которой пришлось разбираться вручную при ручном запуске.

### Почему рестарт даёт новый PID

```
до:    Main PID: 29748    CPU: 10min 24s
после: Main PID: 570064   CPU: 4ms
```

`restart` — это не «перезагрузка» процесса, а `stop` плюс `start`: старый получает сигнал и умирает, затем systemd порождает **совершенно новый** через `fork()` + `execve()`.

PID выдаётся ядром при создании процесса и живёт вместе с ним. Воскресить процесс с тем же номером невозможно — номер освобождается и может достаться кому угодно.

Счётчик CPU обнулился вместе со старым процессом.

**`Active: ... 9ms ago`** — сервис поднялся за 9 миллисекунд. Для `Type=simple` ожидаемо: systemd считает сервис запущенным сразу после `execve()`, не дожидаясь готовности приложения. Порт в этот момент может быть ещё не занят.

### Диагностический индикатор: CPU

```
Active: active (running) since ... ; 14min ago
CPU: 10min 24.332s
```

10 минут процессорного времени за 14 минут работы — почти постоянная загрузка ядра. Это был след busy loop: порт оказался занят посторонним процессом, `nc` падал мгновенно, цикл крутился без блокировки.

**Правило:** счётчик `CPU` в `systemctl status`, растущий сопоставимо со временем работы, означает, что процесс работает вхолостую. Для сервиса, который должен просто ждать соединений, это признак неисправности.

## Logs

### Где хранятся

| Место | Что |
|---|---|
| `/var/log/journal/` | журнал systemd, **бинарный формат**, читается только через `journalctl`. Если каталога нет — журнал в `/run/log/journal/`, то есть в RAM, и стирается при перезагрузке |
| `/var/log/` | классические текстовые логи: `syslog`, `auth.log`, `kern.log`, `dpkg.log` |

Настройка хранения — параметр `Storage=` в `/etc/systemd/journald.conf`.

### Команды

```bash
sudo journalctl -u training-app              # логи конкретного сервиса
sudo journalctl -u training-app -n 50        # последние 50 строк
sudo journalctl -u training-app -f           # следить в реальном времени
sudo journalctl -u training-app -b           # с текущей загрузки
sudo journalctl --since "1 hour ago"         # по времени
sudo journalctl -p err -b                    # только ошибки
journalctl --disk-usage                      # сколько места занимает журнал
```

**`-u` = unit.** Ради этого journald и создавался: раньше логи всех сервисов сваливались в один `syslog`, и нужное приходилось выуживать через `grep`. Теперь systemd знает, какой процесс какому сервису принадлежит.

**Фильтр по времени надёжнее, чем по числу строк.** «Последние 50 записей» могут покрывать и минуту, и неделю — зависит от активности сервиса. `--since` даёт предсказуемый результат.

**`-p` = priority**, уровни 0–7: `emerg`, `alert`, `crit`, `err`, `warning`, `notice`, `info`, `debug`. Указываешь уровень — получаешь его и всё, что серьёзнее.

### Ловушка с правами

```
$ journalctl -u training-app --since "2026-08-24 09:40"
Hint: You are currently not seeing messages from other users and the system.
      Users in groups 'adm', 'systemd-journal' can see all messages.
-- No entries --
```

**`-- No entries --` означает не отсутствие логов, а отсутствие прав.** Journald показывает обычному пользователю только его собственные записи. Нужен `sudo` либо членство в группе `adm` / `systemd-journal`.

Это стоило заметного времени при расследовании — вывод выглядит как «ничего не найдено», хотя записи есть.

### Разница между логами приложения и логами systemd

В журнале сервиса перемешаны два источника, и различать их важно:

```
Aug 26 09:15:48 systemd[1]: training-app.service: Scheduled restart job, restart counter is at 21.
Aug 26 09:15:48 systemd[1]: Started training-app.service - Simple HTTP server listening on port 9000.
Aug 26 09:15:48 app.sh[570166]: 09:15:48 trigger file found, shutting down
Aug 26 09:15:48 systemd[1]: training-app.service: Main process exited, code=exited, status=1/FAILURE
```

**`systemd[1]`** — сообщения менеджера служб: планирование перезапуска, факт старта, фиксация смерти процесса.

**`app.sh[570166]`** — вывод самого приложения в stdout, перехваченный journald.

Первые говорят, **что systemd сделал**; вторые — **что приложение сообщило о себе**. При разборе инцидента нужны оба: приложение объясняет причину, systemd показывает реакцию.

## Crash Test

### Механизм падения

Добавлена проверка файла-триггера в начале цикла:

```bash
        if [ -f /tmp/crash ]; then
            echo "$(date '+%H:%M:%S') trigger file found, shutting down"
            exit 1
        fi
```

**Почему файл-триггер, а не правка кода:** падение вызывается созданием файла, без редактирования скрипта и перезапуска сервиса. Управляемо и повторяемо.

**Почему `/tmp`:** туда может писать любой пользователь. В `/opt/training-app` права только на чтение — файл там создал бы лишь root.

**Почему `exit 1`, а не `exit 0`:** код возврата попадает в журнал и в `systemctl status`. `status=1/FAILURE` честно сообщает об аварийном завершении; `0/SUCCESS` выглядел бы так, будто приложение штатно отработало, и вводил бы в заблуждение.

**Почему проверка перед `echo "waiting"`:** иначе журнал сообщал бы «жду соединения» непосредственно перед смертью. Порядок влияет на достоверность лога.

### Наблюдение

```
09:15:48 systemd[1]: Scheduled restart job, restart counter is at 21.
09:15:48 systemd[1]: Started training-app.service
09:15:48 app.sh[570166]: 09:15:48 trigger file found, shutting down
09:15:48 systemd[1]: Main process exited, code=exited, status=1/FAILURE
09:15:48 systemd[1]: Failed with result 'exit-code'.
09:15:53 systemd[1]: Scheduled restart job, restart counter is at 22.
09:15:53 systemd[1]: Started training-app.service
09:15:53 app.sh[570169]: 09:15:53 trigger file found, shutting down
...
09:16:25 systemd[1]: Scheduled restart job, restart counter is at 28.
```

**Промежуточное состояние**, пойманное между падением и подъёмом:

```
Active: activating (auto-restart) (Result: exit-code) since ...; 1s ago
Process: 570089 ExecStart=/opt/training-app/app.sh (code=exited, status=1/FAILURE)
```

Не `active`, не `failed`, а `activating (auto-restart)` — процесс умер, systemd отсчитывает `RestartSec` и готовится поднять заново.

### Результаты

| Вопрос | Ответ |
|---|---|
| Что сделал systemd | зафиксировал `code=exited, status=1/FAILURE`, классифицировал как `Failed with result 'exit-code'`, запланировал перезапуск |
| Перезапустил? | да, циклически — счётчик дошёл до 28 |
| Интервал | 5–6 секунд, соответствует `RestartSec=5` |
| Новый PID? | каждый раз: 570166 → 570169 → 570172 → 570175 → 570178 → 570181 → 570184 → 570187 |

**`Result: exit-code`** означает, что процесс завершился сам. Другие варианты: `signal` (убит), `timeout`, `core-dump`.

**Шаг PID равен 3** — между попытками ядро выдавало номера другим короткоживущим процессам.

### Почему процесс получает новый PID

Каждый перезапуск создаёт **новый** процесс через `fork()` + `execve()`. Умерший процесс воскресить нельзя, его PID освобождается. То, что systemd называет «restart», — сокращение для «убил старый, породил новый».

Механизм тот же, что при ручном `systemctl restart`; отличается только причина смерти.

### Лимит перезапусков: предсказание не совпало с наблюдением

Ожидалось, что сервис упрётся в защиту от циклического перезапуска и уйдёт в `failed`. Этого не произошло — счётчик дошёл до 28, и перезапуски продолжались.

Разбор умолчаний:

```bash
systemctl show training-app -p StartLimitBurst -p StartLimitIntervalSec
```

`StartLimitBurst=5`, `StartLimitIntervalSec=10s`. Условие срабатывания — **5 стартов внутри окна в 10 секунд**. При `RestartSec=5` интервал между попытками 5–6 секунд, значит в любое десятисекундное окно попадает только два старта. До лимита далеко.

**Практический вывод:** `RestartSec` не просто задаёт паузу, а определяет, упрётся ли сервис в защиту. При `RestartSec=0` приложение улетело бы в `failed` за секунду.

Сброс счётчика после исчерпания лимита: `systemctl reset-failed`.

## Troubleshooting

### Problem

Получена одна строка вводных: сервис `training-app.service` работал вчера, сейчас не работает, восстановить.

Никаких указаний на характер поломки. Возможные варианты из задания: неверный путь, права, пользователь, битая конфигурация юнита, порт, отсутствующая зависимость, падение приложения, переменная окружения.

### Investigation

**Шаг 1. Состояние сервиса**

```
● training-app.service - Simple HTTP server listening on port 9000
     Loaded: loaded (/etc/systemd/system/training-app.service; enabled; preset: enabled)
     Active: activating (auto-restart) (Result: exit-code) since Tue 2026-09-01 10:13:10 UTC; 2s ago
    Process: 650826 ExecStart=/etc/training-app/app.sh (code=exited, status=217/USER)
   Main PID: 650826 (code=exited, status=217/USER)
```

В одной строке **две аномалии**:

**Путь `/etc/training-app/app.sh`** — приложение должно лежать в `/opt/`, не в `/etc/`. Каталог `/etc/` предназначен для конфигурации, исполняемым файлам там не место.

**Код `217/USER`** — не про путь. Означает, что systemd **не смог переключиться на указанного пользователя**. Если бы дело было в отсутствующем файле, код был бы `203/EXEC`.

**Шаг 2. Проверка пользователя**

```
$ id training-app
id: 'training-app': no such user
```

Учётная запись удалена. Это объясняет `217/USER`.

**Важное следствие для порядка работ.** systemd готовит окружение процесса по шагам: сначала пользователь и группа, затем namespace, и только потом `execve()`. Падение на первом шаге означает, что до попытки открыть файл дело не доходит. Значит **неверный путь ещё не проявлялся** — одна поломка маскировала другую.

**Шаг 3. Поиск скрипта**

Каталогов `/opt/training-app/` и `/etc/training-app/` не существует вовсе.

```
$ sudo find / -name "app.sh" 2>/dev/null
/home/Tigran/training-app/app/app.sh          ← исходник для Docker (Task 3)
/var/lib/containerd/.../app/app.sh            ← слои образов Docker
/var/lib/docker/rootfs/.../app/app.sh         ← то же
/opt/trainig-app/app.sh                       ← опечатка, создано в ходе расследования
/opt/app.sh                                   ← искомый файл
```

**Шаг 4. Разделение поломки и собственных действий**

```
$ ls -l /opt/
-rw-r--r-- 1 root root  370 Aug 28 08:03 app.sh
drwx--x--x 4 root root 4096 Aug 28 07:12 containerd
drwxr-xr-x 2 root root 4096 Sep  1 10:16 trainig-app
```

Даты решают вопрос:

| Объект | Дата | Происхождение |
|---|---|---|
| `/opt/app.sh` | **Aug 28 08:03** | день поломки — файл перемещён наставником |
| `/opt/trainig-app/` | **Sep 1 10:16** | сегодня — собственная ошибка с опечаткой в имени, к поломке отношения не имеет |

Проверка дат изменения — тот же приём, что применялся в Task 1 при разборе инцидента с nginx: временная корреляция отделяет чужие изменения от собственных.

**Шаг 5. Права на скрипт**

```
-rw-r--r--  1 root root  370  /opt/app.sh
```

Бит `x` отсутствует **у всех** категорий. Исходно было `-rwxr-xr-x`. Дало бы `203/EXEC` — но только после устранения первых двух поломок.

**Шаг 6. Содержимое скрипта**

```bash
        echo "$(date '+%H:%M:%S') waiting for connection on port 6000"
        echo -e "HTTP/1.1 200 OK\n...\n\nHello from training-app!" | nc -l -p 6000;
```

Порт изменён с 9000 на **6000**, причём в **обеих** строках — и в вызове `nc`, и в тексте лога.

Согласованность делает поломку особенно неприятной: журнал выглядит совершенно нормально и не содержит расхождений. Будь изменена только строка с `nc`, лог сообщал бы «waiting on port 9000» при реально занятом 6000, и несоответствие бросилось бы в глаза.

Обнаружить можно только сопоставив **ожидаемый** порт снаружи с **реально** слушаемым:

```bash
sudo ss -tulpn | grep 9000    # пусто
sudo ss -tulpn | grep 6000    # нашёлся бы app.sh
```

Это ровно тот случай, когда `systemctl status` показывает `active (running)`, `systemctl --failed` пуст, ошибок в журнале нет — а приложение недоступно.

**Шаг 7. Препятствие для починки**

```
$ sudo mv /opt/app.sh /opt/training-app/app.sh
mv: cannot move '/opt/app.sh' to '/opt/training-app/app.sh': Operation not permitted
```

Отказ **от root** — необычно. Обычная нехватка прав дала бы `Permission denied`.

```
$ lsattr /opt/app.sh
----i---------e------- /opt/app.sh
```

Флаг **`i`** — immutable.

### Root Cause

**Шесть отдельных изменений.**

| # | Что сломано | Улика | Симптом |
|---|---|---|---|
| 1 | Удалён пользователь `training-app` | `id` → `no such user` | `217/USER`, блокирует всё остальное |
| 2 | Путь в юните изменён на `/etc/training-app/app.sh` | `ExecStart=` в `status`; каталога не существует | дал бы `203/EXEC` |
| 3 | Скрипт перемещён из `/opt/training-app/` в `/opt/app.sh`, каталог удалён | `find`, дата Aug 28 08:03 | то же |
| 4 | Снят бит исполнения | `-rw-r--r--` вместо `-rwxr-xr-x` | то же |
| 5 | Порт изменён с 9000 на 6000, в обеих строках | `cat` | **`active (running)`, приложение недоступно** |
| 6 | Установлен флаг immutable (`chattr +i`) | `Operation not permitted` от root; `lsattr` | блокирует починку |

**Поломки выстроены слоями**, каждая маскирует следующую:

```
217/USER          → нет пользователя      (падает первым)
   ↓ после исправления
203/EXEC          → неверный путь / нет прав
   ↓ после исправления
active (running)  → но порт 6000 вместо 9000
```

Шестая стоит отдельно: она не в цепочке симптомов, а препятствие для самих исправлений.

### Про флаг immutable

Расширенные атрибуты файловой системы — вторая система ограничений, независимая от прав `rwx`. Права проверяет подсистема разрешений, и root её обходит. Флаги проверяет сама файловая система, **и root не исключение**.

Файл с флагом `i` нельзя изменить, переименовать, переместить, удалить или создать на него жёсткую ссылку. Снять флаг может только процесс с capability `CAP_LINUX_IMMUTABLE` — то есть команда `chattr` от root.

**Ключ к обнаружению — точная формулировка ошибки:**

| Сообщение | errno | Смысл | Куда смотреть |
|---|---|---|---|
| `Permission denied` | `EACCES` | не хватает прав доступа | `ls -l` |
| `Operation not permitted` | `EPERM` | операция запрещена как таковая | `lsattr` |

Второе от root — прямой сигнал проверять атрибуты, а не права.

Буква `e` в выводе `lsattr` — extent format, обычный признак ext4, есть у всех файлов на этой ФС.

Приём применяется и по делу: `chattr +i /etc/resolv.conf` защищает конфиг от перезаписи сетевыми службами, флаг `a` (append-only) не даёт подчистить логи. Обратная сторона — им пользуются и для закрепления в системе.

### Fix

Порядок соответствует порядку срабатывания поломок.

**1. Снять блокировку**

```bash
sudo chattr -i /opt/app.sh
lsattr /opt/app.sh
```

**2. Сохранить улику для отчёта**

```bash
sudo cp /opt/app.sh ~/app-broken.sh
```

**3. Восстановить пользователя**

```bash
sudo useradd -r -M -s /usr/sbin/nologin training-app
```

Те же флаги, что при исходном создании — восстановление должно быть точным, а не просто работающим.

```
$ id training-app
uid=996(training-app) gid=989(training-app) groups=989(training-app)
```

**UID и GID совпали с исходными** — 996 и 989. Номера освободились при удалении учётной записи и были выданы снова.

**4. Вернуть скрипт на место**

```bash
sudo mkdir -p /opt/training-app
sudo mv /opt/app.sh /opt/training-app/app.sh
```

**5. Вернуть право на исполнение**

```bash
sudo chmod +x /opt/training-app/app.sh
```

**6. Исправить порт в скрипте**

```bash
sudo sed -i 's/6000/9000/g' /opt/training-app/app.sh
```

Обе строки — и вызов `nc`, и текст лога.

**7. Исправить путь в юните**

```bash
sudo nano /etc/systemd/system/training-app.service
```

`ExecStart=/etc/training-app/app.sh` → `ExecStart=/opt/training-app/app.sh`

**8. Применить и запустить**

```bash
sudo systemctl daemon-reload
sudo systemctl restart training-app
```

`daemon-reload` обязателен: юнит изменён, а systemd работает с закешированной версией.

**Что намеренно не делалось:** приложение не переустанавливалось и не переписывалось заново, виртуальная машина не пересобиралась — задание это прямо запрещает. Скрипт восстановлен, а не создан заново.

### Verification

Проверка на **трёх уровнях** — они не взаимозаменяемы.

**1. Сервис активен**

```
● training-app.service - Simple HTTP server listening on port 9000
     Loaded: loaded (/etc/systemd/system/training-app.service; enabled; preset: enabled)
     Active: active (running) since Tue 2026-09-01 10:52:42 UTC
   Main PID: 651513 (app.sh)
     CGroup: /system.slice/training-app.service
             ├─651513 /bin/bash /opt/training-app/app.sh
             └─651535 nc -l -p 9000
```

Путь в CGroup корректный, порт в команде `nc` — 9000.

**2. Порт слушается**

```
$ sudo ss -tulpn | grep 9000
tcp LISTEN 0 1 0.0.0.0:9000 users:(("nc",pid=651535,fd=3))
```

**3. Приложение отвечает**

```
$ curl http://localhost:9000
Hello from training-app!
```

**4. Устойчивость**

```
$ sudo systemctl restart training-app && curl http://localhost:9000
Hello from training-app!

$ systemctl is-enabled training-app
enabled

$ systemctl --failed
0 loaded units listed.
```

Сервис переживает перезапуск, остаётся в автозагрузке, сломанных юнитов в системе нет.

Проверка `is-enabled` существенна: без неё возможно, что устранён симптом, а не инцидент — сервис работал бы до первой перезагрузки.

## Recovery Tests

### Restart

```bash
sudo systemctl restart training-app
systemctl status training-app
curl http://localhost:9000
```

**Результат:** сервис поднимается, `Main PID` меняется, счётчики `CPU` и `Memory` обнуляются, приложение отвечает.

Проверялось многократно по ходу работы — в частности, при финальной верификации после устранения поломок.

**Наблюдение:** `Active: ... 9ms ago` — для `Type=simple` systemd считает сервис запущенным сразу после `execve()`, не дожидаясь готовности приложения. Порт в этот момент может быть ещё не занят.

### Process Crash

Проверено в разделе Crash Test через файл-триггер: приложение завершалось с `exit 1`, systemd фиксировал `status=1/FAILURE` и поднимал заново с интервалом 5–6 секунд, счётчик перезапусков дошёл до 28.

**Не выполнено:** отдельный тест с принудительным завершением процесса через `kill`. Это другой сценарий, чем `exit 1`:

| Способ | Что фиксирует systemd |
|---|---|
| `exit 1` | `Result: exit-code`, `status=1/FAILURE` |
| `kill <PID>` (SIGTERM) | `Result: signal`, `status=15/TERM` |
| `kill -9 <PID>` (SIGKILL) | `Result: signal`, `status=9/KILL` |

При `Restart=always` все три приводят к перезапуску, но в журнале выглядят по-разному. Тест стоит провести отдельно.

Дополнительная тонкость: убивать нужно **главный** процесс (`app.sh`), а не дочерний `nc`. Гибель `nc` штатна — она происходит после каждого клиента, и цикл просто порождает новый.

### Reboot

**Не выполнено** — перезагрузка учебной виртуальной машины не проводилась.

Косвенные основания считать, что сервис поднимется:

- `systemctl is-enabled training-app` → `enabled`
- `WantedBy=multi-user.target` — цель, которой система достигает при обычной загрузке (`systemctl get-default` подтверждает `multi-user.target`)
- `After=network.target` обеспечивает порядок относительно сети

Полноценная проверка требует фактической перезагрузки с последующей проверкой `systemctl status` и `curl`.

## What I Learned

**1. Диагностика идёт снизу вверх, а измерение предшествует гипотезе.**

Порядок: подтвердить симптом → снять показания → выдвинуть гипотезу → проверить → исправить → верифицировать. При шести наложенных поломках попытка чинить по одной наугад означала бы несколько кругов с непонятным результатом: каждая правка не давала бы видимого эффекта, потому что следующая поломка маскировалась предыдущей.

Собранная целиком картина (`systemctl cat`, `id`, `ls -l`, `find`, `lsattr`) позволила исправить всё за один проход.

**2. Точная формулировка ошибки — половина диагноза.**

Пары, которые легко спутать и которые указывают на совершенно разные причины:

| | |
|---|---|
| `Permission denied` (EACCES) | `Operation not permitted` (EPERM) |
| не хватает прав → `ls -l` | операция запрещена → `lsattr` |
| `217/USER` | `203/EXEC` |
| проблема с пользователем | не удалось запустить файл |
| `Result: exit-code` | `Result: signal` |
| процесс завершился сам | процесс убит извне |

Отдельный случай — `-- No entries --` от `journalctl`: это отсутствие **прав**, а не отсутствие данных.

**3. «Сервис работает» не означает «приложение доступно».**

Три уровня проверки не взаимозаменяемы: `systemctl status` (процесс жив) ≠ `ss -tulpn` (порт слушается) ≠ `curl` (приложение отвечает). Плюс четвёртый — `is-enabled`, иначе исправлен симптом, а не инцидент.

Поломка с портом 6000 наглядна: все стандартные индикаторы зелёные, `systemctl --failed` пуст, журнал без единой ошибки — и полная недоступность снаружи.

**Дополнительно.** Ряд вещей, которые оказались неочевидными:

- **`Duration` в `systemctl status` определяет тип поломки** — мгновенное падение означает изначально невалидную конфигурацию, падение после периода работы означает изменение на живом сервисе.
- **Счётчик `CPU`, растущий вровень со временем работы**, — признак цикла без блокировки.
- **`enabled` и `running` — разные вещи**, и путаница между ними даёт сервис, который не переживёт перезагрузку.
- **Предсказание может не совпасть с наблюдением**, и это повод разобраться, а не проигнорировать: ожидаемый лимит перезапусков не сработал, потому что `RestartSec=5` растягивает попытки за пределы окна `StartLimitIntervalSec`.
- **`nologin` не мешает systemd** запускать процесс — оболочка участвует только в интерактивном входе.
- **Временные метки файлов отделяют чужие изменения от собственных** — приём, перенесённый из Task 1.

### Почему journalctl показывает «No entries» при существующих логах

**Вопрос:** `journalctl -u nginx --since ...` возвращает `-- No entries --`, хотя сервис заведомо падал и записи должны быть.

**Что подсказал AI:** journald ограничивает доступ по правам — обычный пользователь видит только собственные записи. Требуется `sudo` либо членство в группе `adm` / `systemd-journal`.

**Что я понял:** пустой вывод команды не равнозначен отсутствию данных. Подсказка про группы печатается прямо в выводе, но легко проскакивает мимо внимания, потому что выглядит как справочная информация.

**Как проверил:** повторил команду с `sudo` — записи появились. Дополнительно `id` подтвердил отсутствие групп `adm` и `systemd-journal`.

### Почему mv от root возвращает Operation not permitted

**Вопрос:** `sudo mv` отказывается перемещать файл, хотя выполняется от root.

**Что подсказал AI:** формулировка `Operation not permitted` (EPERM) отличается от `Permission denied` (EACCES) и указывает не на права доступа, а на расширенные атрибуты файловой системы — вероятнее всего флаг immutable.

**Что я понял:** права `rwx` и флаги файла — две независимые системы. Права root обходит, флаги — нет, потому что их проверяет сама файловая система. Соответственно и диагностика разная: `ls -l` для прав, `lsattr` для флагов.

**Как проверил:** `lsattr /opt/app.sh` показал `----i---------e-------`. После `sudo chattr -i` команда `mv` прошла без ошибок. Повторный `lsattr` подтвердил снятие флага.

### Разница между кодами 217/USER и 203/EXEC

**Вопрос:** сервис падает с `status=217/USER`, при этом в юните виден явно неверный путь. Что чинить первым?

**Что подсказал AI:** `217/USER` относится к переключению на пользователя, `203/EXEC` — к запуску исполняемого файла. systemd готовит окружение по порядку: пользователь, затем namespace, затем `execve()`. Падение на первом шаге означает, что до файла дело не дошло.

**Что я понял:** порядок инициализации определяет, какая из нескольких поломок проявится в логах. Пока не устранена первая, остальные невидимы — и это меняет стратегию: сначала собрать полную картину всеми доступными средствами, потом чинить.

**Как проверил:** `id training-app` вернул `no such user`, что соответствует коду. После создания пользователя сервис перестал падать с `217/USER` — и следующей проявилась бы проблема с путём, если бы она не была исправлена в том же проходе.

### Настройка nano для Python

**Вопрос:** ошибка `TabError: inconsistent use of tabs and spaces in indentation`.

**Что подсказал AI:** табы и пробелы визуально неразличимы, но для Python это разные символы. Проверить можно через `cat -A`, где табуляция отображается как `^I`. Постоянное решение — `set tabstospaces` в `~/.nanorc`.

**Что я понял:** в bash отступы декоративны, в Python они часть синтаксиса. Смешение возникает само собой при наборе части строк вручную и части копированием.

**Как проверил:** `cat -A` показал `^I` в проблемных строках. После `sed -i 's/\t/    /g'` файл скомпилировался через `python3 -m py_compile`.
