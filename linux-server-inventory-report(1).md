**Цель задания:** составить техническую инвентаризацию сервера и провести расследование инцидента.

## Часть 1. Операционная система и ядро

### Вопрос: как определить ОС на Linux-сервере?

```bash
cat /etc/os-release      # дистрибутив, версия, кодовое имя
hostnamectl              # ОС + ядро + архитектура + виртуализация одним блоком
lsb_release -a           # то же, но требует пакет lsb-release
```

**Почему именно `/etc/os-release`:**

1. **Стандартизирован systemd.** Раньше у каждого дистрибутива был свой файл — `/etc/redhat-release`, `/etc/debian_version`, `/etc/SuSE-release`. Скрипту приходилось проверять их все. Теперь путь один и он есть везде.
2. **Всегда присутствует.** `lsb_release` — отдельная программа из пакета, которого нет на минимальных образах (Docker, cloud-images). `/etc/os-release` — часть базовой системы.
3. **Формат = валидный shell-синтаксис.** Файл можно подключить прямо в скрипте без парсинга:
   ```bash
   . /etc/os-release
   echo "$ID $VERSION_ID"     # ubuntu 24.04
   ```
4. **Это чтение файла, а не запуск программы.** `lsb_release` — Python-скрипт, читающий те же данные, только медленнее.

Деталь: обычно `/etc/os-release` — симлинк на `/usr/lib/os-release`. Копия в `/usr/lib` от вендора, `/etc` — место для переопределения админом.

Полезные поля: `PRETTY_NAME`, `ID`, `VERSION_ID`.

### Вопрос: как узнать версию ядра?

```bash
uname -r    # только версия ядра
uname -m    # архитектура
uname -a    # всё сразу
```

**Что делает `uname`:** название от *unix name*. Утилита делает системный вызов `uname()` — напрямую спрашивает у работающего ядра «представься». Данные не из конфига, а из памяти, поэтому всегда честные. Тот же источник — `/proc/version`.

**Почему `-r`:** `release` — выводит ровно одно поле, версию ядра, без лишнего. Без ключей `uname` выдаст просто `Linux`, с `-a` версия будет закопана среди hostname и даты сборки.

**Разбор вывода `6.8.0-51-generic`:**

| Часть | Значение |
|---|---|
| `6` | major |
| `8` | minor |
| `0` | patch |
| `51` | номер сборки Ubuntu (ABI) |
| `generic` | flavour — вариант сборки (бывают lowlatency, aws, kvm) |

`6.8.0` — версия upstream от kernel.org. `-51` — Ubuntu накладывает свои патчи и собирает, это порядковый номер сборки.

**Зачем в инвентаризации:** версия ядра определяет доступные фичи (cgroups v2 для Docker/K8s, eBPF, WireGuard) и подверженность известным CVE.

**Отдельно:** установленное и запущенное ядро могут различаться, если после `apt upgrade` не было перезагрузки. Проверка: `dpkg -l | grep linux-image` — если в списке версия новее, чем в `uname -r`, сервер ждёт reboot.

## Часть 2. Аппаратное обеспечение

### Виртуалка или физический сервер

```bash
systemd-detect-virt
```

Возвращает имя гипервизора (`kvm`, `vmware`, `microsoft`) или `none`. **Запускать первым** — от ответа зависит трактовка всего остального: на ВМ данные `dmidecode` синтетические, модель CPU может быть замаскирована, «физические» диски — виртуальные блочные устройства.

### Процессор

```bash
lscpu           # архитектура, ядра, потоки, сокеты, кэш, флаги виртуализации
nproc           # только число логических CPU
```

`lscpu` читает `/proc/cpuinfo` и приводит к читаемому виду. Сырой файл повторяет все поля для каждого ядра — отсюда громоздкость.

Ключевые поля: `Model name`, `CPU(s)`, `Thread(s) per core`, `Core(s) per socket`, `Socket(s)`.

### Память

```bash
free -h                     # RAM и swap, human-readable
sudo dmidecode -t memory    # физические планки: слоты, объём, частота
```

**Главная ловушка: смотреть на `available`, а не на `free`.** Linux намеренно занимает свободную RAM под дисковый кэш (`buff/cache`) — эта память числится занятой, но мгновенно освобождается по запросу приложения. Низкий `free` при большом `available` — норма.

### Диски

```bash
lsblk        # дерево устройств и разделов, точки монтирования
lsblk -f     # + файловая система и UUID
df -h        # занятость по точкам монтирования
sudo fdisk -l
```

`lsblk` отвечает «что есть», `df` — «насколько заполнено». Нужны обе.

### Общая сводка

```bash
sudo lshw -short                        # CPU, память, диски, сеть — одной таблицей
sudo dmidecode -t system -t baseboard   # матплата, вендор, серийник
lspci                                   # устройства на шине PCI
lsusb                                   # USB-устройства
```

**Практический порядок:** `systemd-detect-virt` → `lscpu` → `free -h` → `lsblk` + `df -h` → `sudo lshw -short`.

## Часть 3. Сеть

### IP-адреса и интерфейсы

```bash
ip a         # полностью: адреса, MAC, состояние
ip -br a     # brief — компактная таблица, удобно для отчёта
ip link show # только канальный уровень
```

Как читать:
- `lo` — loopback, `127.0.0.1`, всегда есть
- `ens3` / `eth0` / `enp0s3` — реальные интерфейсы. `eth0` — старая схема именования, `ens3`/`enp0s3` — predictable naming от systemd (по позиции на шине PCI)
- `inet 10.0.10.175/24` — адрес и префикс

`ifconfig` — устаревшая, из пакета `net-tools`, в свежей Ubuntu отсутствует. Везде использовать `ip`.

### Шлюз по умолчанию

```bash
ip r                    # таблица маршрутизации
ip route show default   # только шлюз
ip route get 8.8.8.8    # каким маршрутом реально пойдёт пакет
```

Разбор строки `default via 10.0.10.1 dev ens3 proto dhcp src 10.0.10.175 metric 100`:

| Поле | Значение |
|---|---|
| `default` | маршрут для всего, что не подошло под остальные (0.0.0.0/0) |
| `via 10.0.10.1` | **сам шлюз** |
| `dev ens3` | через какой интерфейс |
| `proto dhcp` | получен по DHCP, не задан вручную |
| `src` | адрес-источник |
| `metric` | приоритет; при нескольких default выбирается наименьший |

### DNS

```bash
cat /etc/resolv.conf     # покажет 127.0.0.53 — это stub systemd-resolved, не настоящий DNS
resolvectl status        # реальные upstream-серверы по каждому интерфейсу
cat /etc/netplan/*.yaml  # источник конфигурации
```

Подвох Ubuntu: `/etc/resolv.conf` почти всегда указывает на локальный stub-резолвер `127.0.0.53`. Настоящие серверы видны только через `resolvectl status` — именно её брать в отчёт.

`ip a` и `resolvectl` показывают **результат**, Netplan — **источник** конфигурации.

### Открытые порты

```bash
sudo ss -tulpn
```

| Флаг | Значение |
|---|---|
| `-t` | TCP |
| `-u` | UDP |
| `-l` | только listening |
| `-p` | показать процесс (требует sudo) |
| `-n` | не резолвить порты в имена |

**Ключевой критерий — адрес перед портом:**
- `0.0.0.0:22` — все IPv4-интерфейсы, **доступен извне**
- `127.0.0.1:3306` — только loopback, снаружи **недоступен**
- `[::]:80` — все IPv6

В графу «exposed» идут только `0.0.0.0` и `[::]`.

Второй слой — файрвол: `sudo ufw status verbose`. Реально доступно то, что открыто **и** в сокетах, **и** в правилах.

`netstat` — устаревшая, `ss` быстрее и стоит по умолчанию.

## Часть 4. Процессы и сервисы

### Разница между процессом и сервисом

**Процесс** — любая запущенная программа. У каждого есть PID и родитель (PPID); процессы образуют дерево.

**Сервис (служба)** — процесс, который запускается автоматически при загрузке, работает в фоне и не привязан к терминалу. Исторически называются **демонами**, отсюда имена на `d`: `sshd`, `systemd`, `containerd`.

**systemd** — менеджер сервисов, он же процесс с PID 1, предок всех остальных.

> **Сервис — это всегда процесс, но не каждый процесс — сервис.** Поэтому `ps`/`top` для процессов, `systemctl` для сервисов.

### Процессы

```bash
ps aux                          # все процессы всех пользователей
ps aux --sort=-%mem | head -15  # топ по памяти
ps aux --sort=-%cpu | head -15  # топ по CPU
ps -ef --forest                 # деревом
top                             # в реальном времени (q — выход, M — память, P — CPU)
htop                            # то же, удобнее
```

`aux` пишется без дефиса — это BSD-синтаксис: `a` — все пользователи, `u` — формат с юзером и нагрузкой, `x` — включая процессы без терминала (то есть демоны).

`ps` — снимок в моменте (для отчёта), `top` — живое наблюдение (для поиска проблемы).

Колонка `STAT`: `S` — спит, `R` — работает, `Z` — зомби.

### Сервисы

```bash
systemctl list-units --type=service --state=running --no-pager
systemctl list-unit-files --type=service --state=enabled --no-pager
systemctl status <имя>
systemctl --failed
```

**Критичное различие:** `enabled` — включён в автозагрузку; `running` — работает прямо сейчас. Сервис может быть enabled, но упавший. Или running, но не enabled — тогда после перезагрузки не поднимется. Для инвентаризации нужны оба списка.

`systemctl --failed` — самая важная команда раздела, ответ бинарный. `0 loaded units listed.` = всё в порядке.

## Часть 5. Логи

### 1. Где хранятся логи?

- **`/var/log/journal/`** — журнал systemd. **Бинарный формат**, читается только через `journalctl`. Взамен — индексация, структурированные поля, быстрая фильтрация. Если каталога нет, журнал в `/run/log/journal/` (в RAM) и стирается при перезагрузке. Настройка: `Storage=` в `/etc/systemd/journald.conf`.
- **`/var/log/`** — классические текстовые логи: `syslog` (общий), `auth.log` (входы, sudo), `kern.log` (ядро), `dpkg.log` (пакеты). Плюс каталоги сервисов: `/var/log/nginx/`, `/var/log/mysql/`.

### 2. Как посмотреть свежие логи?

```bash
journalctl -e          # открыть сразу в конце
journalctl -n 50       # последние 50 строк
journalctl -f          # следить в реальном времени (Ctrl+C)
journalctl -b          # только с текущей загрузки (-b -1 — с предыдущей)
sudo tail -n 50 /var/log/syslog
```

### 3. Логи конкретного сервиса?

```bash
journalctl -u nginx
systemctl status nginx    # покажет последние ~10 строк внизу
```

`-u` = unit. Ради этого journald и создавался: раньше логи всех сервисов сваливались в один `syslog` и приходилось выуживать через `grep`. Теперь systemd знает, какой процесс какому сервису принадлежит.

### 4. Только недавние записи?

```bash
journalctl -u nginx -n 20
journalctl --since "1 hour ago"
journalctl --since today
journalctl --since "2026-08-24 09:40" --until "2026-08-24 09:55"
journalctl -p err -b      # только ошибки
```

Фильтр по времени надёжнее, чем по числу строк: «последние 50 записей» могут покрывать и минуту, и неделю — зависит от активности сервиса.

`-p` = priority, уровни 0–7: `emerg`, `alert`, `crit`, `err`, `warning`, `notice`, `info`, `debug`. Указываешь уровень — получаешь его и всё, что серьёзнее.

Дополнительно: `journalctl --disk-usage` — сколько места занимает журнал (типовая причина заполнения диска на серверах).

## Часть 6. Оценка состояния сервера

| Вопрос | Команда | Критерий вывода |
|---|---|---|
| Высокая нагрузка CPU? | `uptime`, `top` | Сравнить load average с `nproc` |
| Мало памяти? | `free -h` | Колонка **`available`**, не `free`; плюс рост swap |
| Мало места? | `df -h`, `df -i` | >80% — внимание, >90% — риск. Проверять **и inode** |
| Упавшие сервисы? | `systemctl --failed` | Ответ бинарный |
| Открытые порты? | `sudo ss -tulpn`, `ufw status` | Адрес перед портом: `0.0.0.0` vs `127.0.0.1` |
| Топ по CPU? | `ps aux --sort=-%cpu \| head` | В `top` — клавиша `P` |
| Топ по памяти? | `ps aux --sort=-%mem \| head` | Считать по **RSS**, не по VSZ |

### Разбор критериев

**Load average — это не проценты**, а среднее число процессов в очереди на выполнение. Сравнивается с числом ядер:
- load 1.0 на 1 ядре → загружен под завязку
- load 1.0 на 4 ядрах → четверть, всё спокойно
- load 8.0 на 4 ядрах → перегрузка

Три числа (1/5/15 мин) дают динамику: 1-минутное сильно выше 15-минутного — нагрузка растёт сейчас; наоборот — пик прошёл.

В `top` строка `%Cpu(s)`: `us` — пользовательские процессы, `sy` — ядро, `wa` — **ожидание диска**, `id` — простой. Высокий `wa` при низком `us` означает, что упирается не в процессор, а в диск.

**Inode-ловушка:** место может быть, а inode кончиться. Inode — запись о файле, их количество фиксировано при создании ФС. Миллионы мелких файлов исчерпают inode при 20% занятого места, и система выдаст «No space left on device» при формально свободном диске.

**RSS против VSZ:** `RSS` (Resident Set Size) — физическая RAM, реально занятая процессом. `VSZ` (Virtual Size) — всё адресное пространство, включая то, что никогда не загружалось; бывает огромным и сам по себе ни о чём не говорит.

**Процесс может показывать >100% CPU** — значит использует несколько ядер (200% = два ядра полностью).

**OOM killer:** `dmesg -T | grep -i "out of memory"` — если записи есть, памяти не хватало и ядро убивало процессы.

## Часть 7. Инцидент #1 — Web Server Unavailable

**Заявка:** веб-сервер недоступен по `http://localhost:8080`.

### Ход расследования

**Шаг 1 — подтверждение симптома**

```bash
curl -v http://localhost:8080
```

Результат:
```
connect to ::1 port 8080 ... failed: Connection refused
connect to 127.0.0.1 port 8080 ... failed: Connection refused
curl: (7) Failed to connect to localhost port 8080 after 0 ms
```

**Три вывода из этого:**

1. **`Connection refused`, а не `timed out`.** Refused означает, что пакет дошёл до ядра, ядро посмотрело в таблицу сокетов, никого на порту не нашло и вернуло RST → **на порту никто не слушает**. При блокировке файрволом был бы timeout: пакет молча дропается, curl ждёт и сдаётся.
2. **`after 0 ms`** — отказ мгновенный. Файрвол и сетевые проблемы исключены.
3. **Отказ и по `::1`, и по `127.0.0.1`** — curl проверил оба стека, сервис не висит на одном из них. Не запущен вообще.

**Шаг 2 — состояние сервиса**

```bash
systemctl --failed
```
```
● nginx.service loaded failed failed nginx - high performance web server
```

```bash
systemctl status nginx
```
```
Loaded: loaded (/usr/lib/systemd/system/nginx.service; enabled; preset: enabled)
Active: failed (Result: exit-code) since Mon 2026-08-24 09:49:16 UTC; 23h ago
Duration: 8min 38.659s
Process: 4555 ExecStart=/usr/sbin/nginx -c ${CONFFILE} (code=exited, status=1/FAILURE)
```

**Что читается из вывода:**

| Строка | Вывод |
|---|---|
| `enabled` | В автозагрузке. Гипотеза «забыли `enable`» отброшена — он должен был подняться сам |
| `Result: exit-code` | Процесс завершился сам с ненулевым кодом. Не убит сигналом, не таймаут |
| `status=1/FAILURE` | Для nginx код 1 — почти всегда `[emerg]`: конфиг или окружение |
| **`Duration: 8min 38s`** | **Ключевое.** Проработал 8,5 минут и упал. Битый изначально конфиг убил бы его за доли секунды → конфиг был валиден при старте, сломалось потом |
| `09:49:16` | Точное время падения — по нему искать в логах |

**Шаг 3 — препятствие: нет доступа к логам**

```bash
journalctl -u nginx --since ... 
```
```
Hint: You are currently not seeing messages from other users and the system.
      Users in groups 'adm', 'systemd-journal' can see all messages.
-- No entries --
```

`-- No entries --` здесь **не значит, что логов нет**. Journald ограничивает доступ по правам: обычный пользователь видит только свои записи. Нужен `sudo` или членство в группе `adm`/`systemd-journal`.

`sudo` недоступен: `Tigran is not in the sudoers file`.

**Обход — текстовые логи nginx:**

```bash
ls -l /var/log/nginx/
```
```
-rw-r----- 1 nginx adm     0 Aug 25 00:00 access.log
-rw-r----- 1 nginx adm  6565 Aug 24 09:48 access.log.1
-rw-r----- 1 nginx adm     0 Aug 25 00:00 error.log
-rw-r----- 1 nginx adm 15909 Aug 24 09:49 error.log.1
```

**Два наблюдения:**

1. **`error.log.1` изменён Aug 24 09:49** — ровно момент падения. 15909 байт содержимого, там причина.
2. **Текущие логи пусты и датированы `Aug 25 00:00`** — в полночь отработал **logrotate**: переименовал старые в `.1`, создал новые пустые. С тех пор nginx не работает, писать некому. Читать нужно `.1`.

Права `-rw-r----- nginx adm`: владелец `nginx` — чтение+запись, группа `adm` — чтение, остальные — ничего. Доступ закрыт.

**Шаг 4 — обход через конфиг (доступен на чтение)**

```bash
grep -rn "listen" /etc/nginx/
```
```
/etc/nginx/conf.d/default.conf:2:    listen 8080;
/etc/nginx/conf.d/default.conf:3:    listen [::]:8080;
```

Порт 8080 настроен корректно, на обоих стеках. Гипотеза «слушает не тот порт» отброшена — важный отрицательный результат.

**Шаг 5 — корреляция по времени изменения файлов**

```bash
ls -lt --time-style=full-iso /etc/nginx/ /etc/nginx/conf.d/
find /etc/nginx -newermt "2026-08-24 09:00" ! -newermt "2026-08-24 10:00" -ls
```
```
/etc/nginx/conf.d/:
-rw-r--r-- 1 root root 136 2026-08-24 09:49:06 default.conf

/etc/nginx/:
drwxr-xr-x 2 root root 4096 2026-08-24 09:49:06 conf.d
-rw-r--r-- 1 root root  644 2026-07-15 17:49:29 nginx.conf
-rw-r--r-- 1 root root 5349 2026-07-15 17:20:38 mime.types
```

### Найденное доказательство

```
default.conf   изменён  09:49:06
nginx.service  упал     09:49:16
                        ↑
                  разница 10 секунд
```

**Причинно-следственная связь по времени однозначна.** Кто-то отредактировал `default.conf`, сделал reload/restart — nginx умер через 10 секунд.

Подкрепляющие факты:
- Из всего `/etc/nginx/` изменён **только** `default.conf`. Остальные файлы датированы 2026-07-15 (сборка образа) — их не трогали. Круг подозреваемых — один файл.

## Что я усвоил

### Методология

**Диагностика идёт снизу вверх по слоям.** Сначала «слушает ли кто-то порт», потом «а почему нет», потом «что в логах». Прыгать сразу к гипотезе — ошибка.

**Текст ошибки — это уже половина диагноза.** `Connection refused` против `timed out` — принципиально разные причины: отсутствующий слушатель против файрвола. Читать сообщение внимательно до того, как что-то предпринимать.

**Отрицательный результат — тоже результат.** Проверка `grep listen` показала, что порт настроен верно. Это не «ничего не нашёл», а отброшенная гипотеза и сужение круга поиска.

**Догадка без доказательства не считается.** Инженерная ценность — в цепочке: симптом → измерение → гипотеза → подтверждение → правка → верификация. Оценивают именно её, а не скорость угадывания.

**Временные метки — самый сильный вид доказательства.** Совпадение «правка в 09:49:06 → падение в 09:49:16» убедительнее любых рассуждений о том, что могло пойти не так.

**Когда прямой путь закрыт, есть обходные.** Journald недоступен без прав → текстовые логи nginx. Логи недоступны → права на файлы. Логи не прочитать вообще → времена изменения файлов и сам конфиг. К причине почти всегда ведёт больше одного маршрута.

**Верификация нужна на нескольких уровнях.** «Сервис активен» ≠ «порт слушается» ≠ «приложение отвечает». Проверять все три, плюс устойчивость к перезагрузке (`enabled`).

### Технические выводы

- **`available`, а не `free`** — при оценке памяти. Дисковый кэш числится занятым, но освобождается мгновенно.
- **Load average сравнивается с числом ядер**, это не проценты, а длина очереди.
- **`df -i` наравне с `df -h`** — inode кончаются раньше места при большом числе мелких файлов.
- **RSS, а не VSZ** — при оценке памяти процесса.
- **Адрес перед портом важнее самого порта:** `0.0.0.0` — наружу, `127.0.0.1` — нет.
- **`enabled` ≠ `running`** — включён в автозагрузку и работает сейчас это разные вещи.
- **Пустой вывод может означать отсутствие прав, а не отсутствие данных** — `journalctl` с его `-- No entries --` тому примером.
- **`Duration` в `systemctl status`** говорит, когда сломалось: мгновенное падение — конфиг битый изначально, падение после работы — сломали в процессе.
- **logrotate объясняет пустые логи** — свежие файлы с датой полуночи и нулевым размером означают, что смотреть надо в `.1`.
- **`nginx -t` работает без прав на логи** — парсинг конфига идёт до открытия лог-файлов.
- **Устаревшие команды из `net-tools`** (`ifconfig`, `netstat`, `route`) заменены на `ip` и `ss`.
- **`journalctl` фильтрует по времени и по важности** (`--since`, `-p err`) — надёжнее, чем по числу строк.

journalctl --disk-usage
ls -l /var/log/nginx/

curl -v http://localhost:8080
curl -I http://localhost:8080
nginx -t
grep -rn "listen" /etc/nginx/
ls -lt --time-style=full-iso /etc/nginx/ /etc/nginx/conf.d/
