## Troubleshooting Exercise

### Problem

Веб-сервер недоступен по `http://localhost:8080`. Запрос возвращает `Connection refused` на обоих стеках (`::1` и `127.0.0.1`) за 0 мс.

Мгновенный отказ вместо таймаута означает, что пакет дошёл до ядра, слушателя на порту не нашлось и вернулся RST. Файрвол и сетевые проблемы исключаются: при блокировке пакет отбрасывается молча и клиент ждёт таймаута.

`ss -tulpn` подтверждает: порт 8080 никем не занят.

### Investigation

**Состояние сервиса.** `nginx.service` в состоянии `failed` с 2026-08-24 09:49:16 UTC, код возврата 1. Сервис числится `enabled`, то есть должен подниматься при загрузке — значит это неисправность, а не намеренно выключенная служба.

Поле `Duration: 8min 38s` задало направление поиска: сервис проработал восемь с половиной минут и упал. Изначально невалидный конфиг убил бы его за доли секунды при старте — следовательно, конфигурация была рабочей и сломалась в процессе.

**Препятствие.** Журнал systemd оказался недоступен: обычному пользователю journald показывает только его собственные записи, а учётная запись Tigran не входила в sudoers. Текстовые логи nginx также закрыты правами (`nginx:adm`). Пустой вывод `journalctl` при этом означал не отсутствие логов, а отсутствие прав.

**Обходные пути.** Каталог `/etc/nginx/` доступен на чтение всем, что позволило продолжить расследование.

Проверка директив `listen` показала корректно настроенный порт 8080 на обоих стеках — гипотеза «сервис слушает не тот порт» отброшена.

Сравнение времени изменения файлов дало ключевую зацепку: из всего каталога `/etc/nginx/` свежую дату имеет только `default.conf` (09:49:06), остальные файлы датированы днём сборки образа.

**Валидация конфигурации.** `nginx -t` выполняет разбор конфигурации до открытия лог-файлов и потому работает без привилегий. Вывод содержал три сообщения, но фатально только одно:

- `[alert]` о недоступном `error.log` — следствие запуска без root
- `[warn]` об игнорируемой директиве `user` — то же самое
- **`[emerg]` — неизвестная директива `flag_name`, строка 9**

Для nginx фатален только уровень `[emerg]`.

### Root Cause

В файл `/etc/nginx/conf.d/default.conf` на строку 9 добавлена директива `flag_name`, которой в nginx не существует:

```nginx
8	    server_name _;
9	    flag_name   _;    ← несуществующая директива
```

Строка 8 легитимна — `server_name _` это стандартный catch-all. Строка 9 представляет собой её копию с изменённым именем директивы.

При разборе конфигурации nginx завершается с ошибкой `unknown directive`, отсюда состояние `failed` и незанятый порт 8080.

**Причина подтверждена двумя независимыми методами:**

1. **Валидатор конфигурации** указал конкретный файл и номер строки.
2. **Временная корреляция:** файл изменён в 09:49:06, сервис упал в 09:49:16 — разница 10 секунд. Правка и последовавший reload уронили сервис.

**Подтверждающие факты:** изменён единственный файл в каталоге; `Duration` показывает, что сервис работал до правки; `access.log` содержит записи вплоть до 09:48; сервис числится `enabled`; конкурента за порт 8080 в системе нет — ни apache2, ни docker не установлены.

### Resolution

Строка 9 удалена, изменение зафиксировано через `diff` с резервной копией: единственное отличие — удалённая директива `flag_name`.

Порядок действий: бэкап конфигурации → правка → валидация через `nginx -t` **до** перезапуска (чтобы не ронять сервис повторно) → запуск → проверка.

Верификация проводится на трёх уровнях, они не взаимозаменяемы: сервис активен (`systemctl status`), порт слушается (`ss -tulpn`), приложение отвечает (`curl -I` → `HTTP/1.1 200 OK`). Дополнительно — устойчивость к перезапуску и статус `enabled`, иначе устранён симптом, а не инцидент.

### Выводы

**Уровни важности в логах нужно различать.** Из трёх сообщений `nginx -t` фатальным было только `[emerg]`; попытка чинить `[alert]` и `[warn]` увела бы расследование в сторону.

**`Duration` определяет тип поломки.** Мгновенное падение указывает на изначально битый конфиг, падение после периода работы — на правку живого сервиса.

**Отсутствие прав не блокирует диагностику.** Журнал был закрыт, логи нечитаемы, sudo недоступен — причину нашли через времена изменения файлов и валидатор, работающий без привилегий.

**Отрицательный результат сужает поиск.** Корректный порт в конфиге и отсутствие конкурирующего веб-сервера отбросили две гипотезы до того, как на них ушло время.

**Верификация обязательна на нескольких уровнях.** «Сервис запущен» не равно «порт слушается» не равно «приложение отвечает».
